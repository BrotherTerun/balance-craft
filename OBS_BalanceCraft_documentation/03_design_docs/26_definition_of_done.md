# 26. Definition of Done

## Назначение

Этот документ фиксирует критерии готовности для функций, фаз и BalanceCraft Desktop 1.5 в целом.

DoD нужен, чтобы не принимать “оно вроде работает на моём ноуте, если не трогать вот эту кнопку” за готовую фичу. Особенно после большого рефакторинга, где старый прототип уже доказал идею, но новая версия должна доказать архитектуру.

## Главный принцип готовности

Фича считается готовой не тогда, когда у неё появился код, а когда она:

```text
работает в новом local-first runtime;
не зависит от MySQL;
использует универсальную модель данных;
понятна пользователю;
не создаёт false-аналитику;
проверена вручную или тестом;
не ломает vertical slice.
```

# 1. Общий DoD для любой функции

Функция готова, если выполнены все обязательные пункты.

## Функциональность

- [ ] Функция реализована в новом кодовом пути BalanceCraft 1.5.
- [ ] Функция работает после перезапуска приложения.
- [ ] Функция работает на локальной SQLite-БД.
- [ ] Функция не требует MySQL, PostgreSQL, Docker, сервера или админских прав.
- [ ] Функция не зависит от старых таблиц `players`, `sessions`, `items`, `skills` как обязательного ядра.
- [ ] Функция возвращает структурированный результат, если вызывается через backend/frontend bridge.
- [ ] Функция имеет понятный success path.
- [ ] Функция имеет понятный failure path.

## Данные

- [ ] Raw-события не изменяются без явной причины.
- [ ] Производные данные сохраняются отдельно от raw events.
- [ ] Все пользовательские данные привязаны к `project_id`, если это проектные данные.
- [ ] JSON-поля не теряют исходные данные.
- [ ] Ошибки частичной обработки не оставляют проект в невалидном состоянии.
- [ ] Транзакции используются там, где возможна частичная запись.

## UX и ошибки

- [ ] Пользователь видит следующий разумный шаг.
- [ ] Empty state объясняет, что нужно сделать.
- [ ] Ошибка написана человеческим языком.
- [ ] Технические details доступны для диагностики, но не являются основным текстом ошибки.
- [ ] UI не показывает сырые stack traces как пользовательское сообщение.
- [ ] Warnings не скрываются, если они влияют на интерпретацию результата.

## Честность аналитики

- [ ] Функция не делает выводы без достаточных данных.
- [ ] Ограничения результата показаны пользователю.
- [ ] `N/A` не заменяется искусственным числом.
- [ ] Деление на ноль или почти нулевой знаменатель даёт warning/`N/A`.
- [ ] ROI не называется ROI, если cost и result не приведены к общей шкале.
- [ ] Сценарный результат имеет confidence status, если относится к What-if.
- [ ] Каждый insight имеет evidence.

## Терминология

- [ ] В ядре используются `entity`, `observation`, `event`, `attribute`, `parameter`, `metric`, `binding`, `scenario`.
- [ ] `player`, `session`, `item`, `skill` используются только как demo/user semantics или legacy references.
- [ ] UI не продаёт BalanceCraft как RPG-only progression analyzer.
- [ ] Тексты согласованы с glossary.

## Проверка

- [ ] Есть ручной тест-кейс или автоматический тест.
- [ ] Функция проверена на demo project, если она пользовательская.
- [ ] Функция не ломает импорт JSONL.
- [ ] Функция не ломает dashboard.
- [ ] Функция не ломает запуск приложения без MySQL.

---

# 2. DoD для P0-функции

P0-функция готова только если дополнительно:

- [ ] Она участвует в основном vertical slice или явно поддерживает его.
- [ ] Без неё MVP не считается готовым.
- [ ] Она имеет минимальный UI или backend path, достаточный для demo.
- [ ] Она имеет human-readable errors.
- [ ] Она не требует P1/P2-зависимостей для базового сценария.
- [ ] Её можно объяснить в README или demo scenario.

Пример: `JSONL import` готов только если пользователь реально может выбрать файл/папку, импортировать события, увидеть отчёт и перейти к data map. Просто функция парсинга JSONL в коде — это ещё не готовый import.

---

# 3. DoD для P1-функции

P1-функция готова, если:

- [ ] Все связанные P0-функции уже стабильны.
- [ ] Функция улучшает портфолио-демо, UX или устойчивость.
- [ ] Функция не усложняет первый пользовательский путь.
- [ ] Функцию можно отключить или вырезать без разрушения MVP.
- [ ] Документация не подаёт её как обязательное свойство 1.5, если она всё ещё экспериментальная.

---

# 4. DoD для P2/P3-функции

P2/P3-функция не считается частью BalanceCraft 1.5.

Она может быть:

- описана в документации;
- учтена в формате данных;
- учтена в архитектурных расширениях;
- упомянута в roadmap.

Но она не должна:

- блокировать Desktop vertical slice;
- требовать отдельного сервера для запуска MVP;
- расширять scope 1.5;
- появляться в README как готовая возможность;
- менять privacy posture local-first продукта.

# 5. DoD по компонентам

## 5.1. Project management

Готово, если:

- [ ] Новый проект создаётся без ручного SQL.
- [ ] Проект открывается после перезапуска.
- [ ] Recent projects работает или есть минимальная замена.
- [ ] Demo project доступен с первого экрана.
- [ ] Ошибки открытия проекта понятны пользователю.

## 5.2. SQLite / DB layer

Готово, если:

- [ ] Приложение запускается без MySQL.
- [ ] SQLite-БД создаётся автоматически.
- [ ] Нет hardcoded root password.
- [ ] Нет `CREATE DATABASE` в runtime.
- [ ] Нет `INFORMATION_SCHEMA` в runtime.
- [ ] Все запросы используют SQLite placeholders.
- [ ] Включены foreign keys.
- [ ] Импорт и расчёт используют транзакции.
- [ ] Есть минимальные индексы.

## 5.3. Import service

Готово, если:

- [ ] JSONL-файл импортируется.
- [ ] Папка с JSONL-файлами импортируется или есть понятное ограничение до одного файла.
- [ ] Битые строки не валят весь импорт.
- [ ] Ошибки содержат файл и номер строки.
- [ ] Import report показывает read/valid/invalid/imported counts.
- [ ] События сохраняются в `events.attributes_json` без потери raw attributes.
- [ ] Создаются/обновляются entities и observations.
- [ ] Старые players/sessions не создаются как обязательная модель.

## 5.4. Data profiling

Готово, если:

- [ ] Видны event types и counts.
- [ ] Видны attributes по event type.
- [ ] Видны типы значений.
- [ ] Видны samples.
- [ ] Видны numeric ranges.
- [ ] Смешанные/грязные поля дают warnings.
- [ ] Эти данные можно использовать в Binding Wizard.

## 5.5. Semantic Binding Wizard

Готово, если:

- [ ] Пользователь выбирает template.
- [ ] Пользователь видит переменные template.
- [ ] Пользователь выбирает event_type filters.
- [ ] Пользователь выбирает source path.
- [ ] Пользователь выбирает aggregation или использует понятный default.
- [ ] Система валидирует несовместимые типы.
- [ ] Binding сохраняется.
- [ ] Binding можно открыть после перезапуска.
- [ ] Metric run сохраняет binding snapshot.

## 5.6. Metric templates

Готово, если:

- [ ] Каждый template имеет key.
- [ ] Каждый template имеет variables.
- [ ] Каждый template имеет formulas.
- [ ] Каждый template имеет labels/descriptions.
- [ ] Каждый template описывает ограничения.
- [ ] Формулы используют `safe_div`, где нужен division.
- [ ] Template не требует конкретного жанра или игрока.

## 5.7. Metric engine

Готово, если:

- [ ] Metric run создаётся из semantic bindings.
- [ ] Metric values сохраняются отдельно.
- [ ] Raw events не изменяются.
- [ ] Status/warnings сохраняются или возвращаются API.
- [ ] Деление на ноль не маскируется.
- [ ] Формулы сохраняются snapshot-ом.
- [ ] Расчёт можно повторить без повторного импорта.
- [ ] Результаты можно отдать dashboard.

## 5.8. Dashboard

Готово, если:

- [ ] Пользователь может выбрать metric run.
- [ ] График строится.
- [ ] Подписи понятны.
- [ ] Scope selector не является player-only.
- [ ] `N/A` и warnings не скрываются.
- [ ] Empty state объясняет, почему графика нет.

## 5.9. Practical insights

Готово, если:

- [ ] Insight engine получает рассчитанные ряды.
- [ ] Есть хотя бы один insight для demo/P0-шаблона.
- [ ] Каждый insight имеет severity.
- [ ] Каждый insight имеет recommendation.
- [ ] Каждый insight имеет evidence.
- [ ] Insight не заявляет причинность там, где есть только симптом.

## 5.10. Analysis coverage

Готово, если:

- [ ] Coverage показывает доступные P0-проблемы.
- [ ] Coverage показывает missing data для недоступных проблем.
- [ ] Coverage не блокирует доступные расчёты.
- [ ] Unsupported in version не выглядит как ошибка пользователя.
- [ ] Пользователь понимает, какие события/поля нужно логировать дополнительно.

## 5.11. What-if

Готово, если:

- [ ] Есть parameter или demo parameter для изменения.
- [ ] Scenario override не меняет raw events.
- [ ] Scenario result не перезаписывает historical metric values.
- [ ] UI показывает confidence status.
- [ ] UI объясняет ограничение “sequence событий не меняется”.
- [ ] При отсутствии модели система показывает `insufficient_model`, а не точный прогноз.

Если эти условия не выполнены, What-if лучше оставить вырезанным из текущего MVP, чем выпускать как красивую ложь с графиком.

## 5.12. Demo project

Готово, если:

- [ ] Открывается с первого экрана.
- [ ] Не требует внешних файлов от пользователя.
- [ ] Использует тот же формат данных, что обычный import.
- [ ] Показывает data map.
- [ ] Показывает binding или готовую конфигурацию.
- [ ] Показывает metric chart.
- [ ] Показывает practical insight.
- [ ] Демонстрирует 2–3 понятные проблемы баланса.
- [ ] Не выдаёт синтетические данные за реальные плейтесты.

---

# 6. DoD для phase completion

Фаза implementation checklist считается закрытой, если:

- [ ] Все P0-пункты фазы выполнены.
- [ ] P1-пункты либо выполнены, либо явно перенесены.
- [ ] Приложение запускается.
- [ ] Основной vertical slice не сломан.
- [ ] Есть ручная проверка.
- [ ] Нет новых runtime-зависимостей от MySQL.
- [ ] Документация или checklist обновлены, если решение изменилось.

# 7. DoD для BalanceCraft Desktop 1.5

BalanceCraft Desktop 1.5 готов как портфолио-MVP, если выполнено:

## Runtime

- [ ] Приложение запускается локально.
- [ ] Приложение не требует MySQL.
- [ ] Приложение не требует сервера.
- [ ] Приложение не требует регистрации.
- [ ] SQLite-БД создаётся автоматически.
- [ ] Данные не отправляются наружу.

## Project flow

- [ ] Пользователь может открыть demo project.
- [ ] Пользователь может создать новый проект.
- [ ] Проект открывается после перезапуска.

## Import flow

- [ ] Пользователь может импортировать JSONL.
- [ ] Import report показывает валидные и невалидные события.
- [ ] Ошибки импорта содержат файл и строку.
- [ ] Raw events сохраняются без преждевременной интерпретации.

## Data understanding

- [ ] Data map показывает event types.
- [ ] Data map показывает attributes.
- [ ] Data map показывает типы, samples и warnings.
- [ ] Analysis coverage показывает, что можно и нельзя проверить.

## Semantic layer

- [ ] Пользователь может настроить semantic binding.
- [ ] Binding сохраняется.
- [ ] Binding не требует RPG-таблиц.

## Metrics

- [ ] Считается минимум один P0-шаблон end-to-end.
- [ ] Желательно считаются 2–4 P0-шаблона.
- [ ] Metric run сохраняется отдельно.
- [ ] Metric values сохраняют status/warnings.
- [ ] Формулы не создают ложную точность.

## Dashboard

- [ ] График строится.
- [ ] Пользователь понимает, что изображено.
- [ ] `N/A` и warnings видны.
- [ ] Старый player-only selector заменён или обобщён.

## Insights

- [ ] Показывается хотя бы один practical insight.
- [ ] Insight содержит evidence.
- [ ] Insight содержит recommendation.
- [ ] Insight не обещает больше, чем позволяют данные.

## What-if, если включён

- [ ] Scenario не меняет историю.
- [ ] Scenario имеет confidence status.
- [ ] UI явно показывает ограничения сценария.

## Portfolio

- [ ] README объясняет продукт.
- [ ] Quick start не требует MySQL.
- [ ] Есть demo scenario.
- [ ] Есть скриншоты или готовность их сделать.
- [ ] Roadmap честно отделяет готовое от будущего.

# 8. Release blockers

BalanceCraft 1.5 нельзя считать готовым, если есть хотя бы один blocker.

## Critical blockers

- [ ] Приложение требует MySQL для запуска.
- [ ] В коде есть root password или hardcoded production secret.
- [ ] JSONL import не работает.
- [ ] Нет demo project.
- [ ] Нет data map.
- [ ] Нет рабочего metric run.
- [ ] Нет графика.
- [ ] Raw events мутируются при расчёте.
- [ ] Ошибки показываются как stack trace без человеческого сообщения.
- [ ] UI обещает симуляцию там, где есть только approximation.
- [ ] Данные отправляются наружу без явной настройки пользователя.

## Major blockers

- [ ] Система всё ещё выглядит как RPG-only analyzer.
- [ ] Binding Wizard зависит от `players/sessions` как обязательной модели.
- [ ] Metric engine считает через старый `session_metrics` как ядро.
- [ ] `safe_div` не реализован.
- [ ] Warnings теряются.
- [ ] Insights не имеют evidence.
- [ ] Demo не показывает практическую пользу.

# 9. Acceptance scenario для MVP

Минимальная демонстрация готовности:

```text
1. Запустить BalanceCraft Desktop.
2. Открыть demo project.
3. Увидеть стартовый dashboard или перейти к data map.
4. Открыть data map и увидеть event_type/attributes.
5. Открыть Binding Wizard.
6. Проверить или настроить binding для “Баланса потоков”.
7. Запустить metric calculation.
8. Открыть dashboard.
9. Увидеть график net flow / ratio.
10. Увидеть insight с evidence.
11. Увидеть analysis coverage.
12. Закрыть приложение.
13. Открыть приложение снова.
14. Открыть тот же проект.
15. Убедиться, что данные, bindings и metric runs сохранились.
```

Если этот сценарий проходит, BalanceCraft уже можно показывать как рабочий vertical slice.

# 10. Что не считается готовностью

Не считается готовым:

- “код есть, но UI не подключён” для пользовательской P0-фичи;
- “работает только на моём старом MySQL”;
- “работает только на одном захардкоженном demo JSON”;
- “ошибка понятна, если открыть консоль Python”;
- “график есть, но непонятно, какие данные он показывает”;
- “insight есть, но без evidence”;
- “What-if есть, но без confidence status”;
- “мы потом объясним это в README”.

Увы, README — не святой паладин. Он не должен танковать архитектурные дыры.

# 11. Итоговая формула готовности

```text
BalanceCraft 1.5 готов,
когда пользователь может локально импортировать или открыть демо,
понять структуру данных,
назначить смысл событиям,
получить честные метрики,
увидеть график,
прочитать объяснимый вывод
и не столкнуться с серверной/SQL-инфраструктурой.
```
