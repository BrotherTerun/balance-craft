# 02. Продуктовая рамка BalanceCraft

## Короткое описание

BalanceCraft — локальное desktop-приложение для анализа числового баланса игровых систем на основе событийной телеметрии.

Система принимает игровые события, показывает структуру данных, позволяет разработчику назначить данным смысл через мастер семантики, рассчитывает метрики по универсальным шаблонам, строит графики и помогает проверить простые сценарии изменения параметров.

## Главная формула продукта

```text
Сырые события игры
→ карта данных
→ ручная семантическая привязка
→ универсальные метрики
→ графики и практические выводы
→ простой сценарный анализ параметров
```

## Что BalanceCraft делает

- Импортирует локальные события из JSONL.
- Хранит raw-события без преждевременной интерпретации.
- Строит карту данных: типы событий, поля, частоты, типы значений, примеры.
- Даёт пользователю назначить смысл полям через Binding Wizard.
- Считает метрики по шаблонам анализа.
- Строит временные ряды и сравнения.
- Генерирует практические выводы с основанием вывода.
- Показывает, какие классы проблем можно проверить по текущим данным, а какие нельзя из-за отсутствующих событий или параметров.
- Даёт проверить простые сценарии What-if без изменения исторических данных.

## Какие классы проблем покрывает продукт

BalanceCraft работает с классами проблем, описанными в `01_problem_audience.md`: потоками ресурсов, прогрессией, конверсией, доступностью операций, использованием контента, ритмом наград и динамикой временных рядов.

В рамках продуктовой рамки важно не перечисление каждой проблемы, а общий принцип: BalanceCraft ищет измеримые симптомы числового баланса, показывает основание вывода и честно сообщает, какие проблемы можно или нельзя проверить по текущему набору данных.

Подробная таблица проблем, симптомов и необходимых данных находится в `01_problem_audience.md`.

## Что BalanceCraft не делает

- Не является маркетинговой аналитикой.
- Не заменяет Steamworks, Unity Analytics или GameAnalytics.
- Не заменяет Machinations как визуальный симулятор экономики.
- Не пытается автоматически понять смысл всех игровых данных.
- Не обещает точную симуляцию произвольной игры по сырым логам.
- Не ставит игре абсолютный диагноз без контекста разработчика.
- Не требует облака, регистрации, собственного сервера или внешней СУБД.
- Не собирает данные игроков на серверы авторов BalanceCraft.

## Продуктовые компоненты

### BalanceCraft Desktop

Основной продукт версии 1.5.

Назначение:

- локальный импорт данных;
- локальное хранение;
- профилирование событий;
- настройка семантики;
- расчёт метрик;
- визуализация;
- практические выводы;
- простой What-if.

### BalanceCraft SDK Lite

Библиотека для записи событий из игры в формате, обрабатываемом BalanceCraft.

Для версии 1.5 SDK не является обязательной частью MVP, но формат событий должен проектироваться так, чтобы SDK можно было добавить без смены модели данных.

Минимальная цель SDK Lite:

- `TrackEvent` / `Track`;
- автоматический `timestamp`;
- поддержка `entity_id` и `observation_id`;
- локальная запись JSONL;
- ограничение размера кэша;
- отсутствие скрытых сетевых отправок.

### BalanceCraft Self-hosted Collector

Опциональная серверная часть будущей версии. Разворачивается разработчиком игры, принимает события от SDK, валидирует их, хранит raw-события и отдаёт экспорт для Desktop.

Не входит в MVP 1.5.

### BalanceCraft Cloud

Гипотетическая централизованная облачная версия, в которой серверы авторов BalanceCraft принимали бы, хранили и обрабатывали телеметрию проектов разных разработчиков.

В реализуемых версиях BalanceCraft Cloud не рассматривается как продуктовый компонент. Термин нужен только для фиксации архитектурной альтернативы, от которой проект сознательно отказывается.

Причины отказа:
- противоречит local-first рамке BalanceCraft 1.5;
- создаёт лишнюю инфраструктурную стоимость;
- переносит ответственность за хранение пользовательской телеметрии на авторов BalanceCraft;
- усложняет privacy, retention, security и юридические требования;
- смещает продукт из портфолио-инструмента анализа баланса в сторону SaaS-платформы;
- не нужен для базового сценария “импортировал локальный лог → получил анализ”.

## Режимы работы

| Режим                 | Статус                               | Назначение                                       |
| --------------------- | ------------------------------------ | ------------------------------------------------ |
| Local Mode            | основной для 1.5                     | локальные логи, демо, QA, плейтесты              |
| Self-hosted Collector | будущая версия                       | массовая телеметрия на сервере разработчика игры |
| BalanceCraft Cloud    | отклонённая альтернатива, не входит в реализуемые версии | централизованное облако авторов BalanceCraft |

## Принципы продукта

### 1. Универсальность вместо жанровой привязки

В ядре нет обязательных игроков, предметов, навыков, юнитов, квестов, опыта или уровней. Всё это может быть пользовательской семантикой конкретного проекта анализа, но не фундаментом архитектуры.

### 2. События — нейтральные данные

Событие фиксирует, что произошло. Оно не обязано быть действием игрока и не обязано иметь заранее известный смысл.

### 3. Поздняя семантика

Система не угадывает, что поле означает. Пользователь сам связывает поля данных с переменными шаблона.

### 4. Параметры важнее производных потоков

Для What-if нужно менять реальные параметры сущностей: стоимость, награду, шанс, лимит, множитель, кулдаун. Производные метрики используются как результат анализа, а не как главный рычаг изменения.

### 5. Локальность по умолчанию

Первый рабочий сценарий не требует сервера, регистрации, MySQL, Docker, админских прав или интернета.

### 6. Честность выводов

Выводы должны показывать основание вывода и степень уверенности. Если данных или модели недостаточно, система должна прямо сообщать об этом.

## Минимальный образ BalanceCraft 1.5

```text
Приложение запускается локально.
База SQLite создаётся автоматически.
Пользователь открывает демо или импортирует JSONL.
Система показывает карту данных.
Пользователь настраивает семантику.
Система считает метрики и строит графики.
Система показывает практические выводы.
Пользователь меняет параметр в простом What-if.
Исторические данные не изменяются.
```
