# 14. Риски, допущения и открытые вопросы

## Риски продукта

### R-1. Продукт станет слишком сложным

Описание: сущности, параметры, события, шаблоны, сценарии и confidence statuses могут перегрузить пользователя.

Контрмеры:

- простой демо-проект;
- линейный первый сценарий;
- мастер семантики;
- карта данных;
- расширенные настройки не обязательны для первого результата.

### R-2. Потеря универсальности

Описание: код может снова скатиться к игрокам, сессиям, предметам, навыкам и RPG-прогрессии.

Контрмеры:

- ядро только `entities/events/observations/parameters`;
- жанровые термины только в demo/user semantics;
- регулярный grep по legacy terms.

### R-3. False-аналитика

Описание: система может делать уверенные выводы на неполных или неправильно связанных данных.

Контрмеры:

- ручное подтверждение семантики;
- основание вывода в каждом выводе;
- предупреждения о недостатке данных;
- статусы уверенности What-if.

### R-4. Нереалистичный What-if

Описание: пользователь может воспринять сценарный прогноз как точную симуляцию игры.

Контрмеры:

- уровни What-if;
- явные ограничения;
- статус уверенности;
- формулировка “оценка влияния”, а не “полная симуляция”.

### R-5. Портфолио не считывает ценность

Описание: проект может быть технически интересным, но непонятным для читателя GitHub.

Контрмеры:

- README с коротким value proposition;
- скриншоты;
- demo scenario;
- GIF/видео первого сценария;
- минимальный quick start.


### R-10. Таксономия проблем раздует MVP

Описание: расширенный список проблем баланса может создать впечатление, что версия 1.5 обязана поддерживать всё сразу.

Контрмеры:

- разделить проблемы на P0/P1/P2;
- показывать неподдержанные проблемы как `unsupported_in_version`, а не скрывать их;
- не добавлять шаблон, пока нет понятных входных данных, метрик и основания вывода;
- в демо показывать только те проблемы, которые реально поддержаны.

### R-11. Формулы создают ложную точность

Описание: простые отношения и агрегаты могут выглядеть точнее, чем они есть, особенно при нулевых знаменателях, малой выборке или несопоставимых единицах.

Контрмеры:

- использовать `safe_div` и возвращать `N/A` вместо искусственного деления на `1`;
- показывать предупреждения о малой выборке и отсутствующих данных;
- не называть метрику ROI, если cost и result не приведены к общей шкале;
- хранить calculation warnings вместе с metric run;
- выводить пороги плато, скачков и волатильности явно.


### R-12. Детализация будущих компонентов раздует scope

Описание: подробные требования к SDK Lite и Self-hosted Collector могут создать впечатление, что эти компоненты нужно реализовать в рамках BalanceCraft 1.5.

Контрмеры:

- явно маркировать SDK Lite как P2, Self-hosted Collector как P3;
- в `09_mvp_scope_timeline.md` фиксировать, что эти требования не расширяют 48-часовой MVP;
- для версии 1.5 реализовывать только совместимый формат данных и local import;
- не начинать SDK/Collector до готового Desktop vertical slice.

### R-13. `confidence_status` воспринимается как вероятность

Описание: пользователь может принять статус уверенности за статистическую вероятность или строгую математическую гарантию.

Контрмеры:

- описывать `confidence_status` как rule-based классификацию;
- показывать статус рядом с ограничениями сценария;
- не использовать проценты уверенности в MVP;
- ссылаться на правила из `05_what_if_levels.md`.

### R-14. Value normalization и пользовательские формулы раздуют Binding Wizard

Описание: попытка добавить пользовательские формулы и редактор нормализации ценности в MVP может резко увеличить сложность UI и metric engine.

Контрмеры:

- пользовательские формулы не входят в 1.5;
- нормализованный ROI считать только при наличии `cost_value/result_value/value_unit`;
- value normalization profile оставить P1/P2;
- в MVP использовать заранее описанные формулы шаблонов и formula snapshots.

### R-15. 48 часов воспринимаются как оценка полной стабильной версии

Описание: ограничение 48 часов может быть прочитано как обещание сделать production-ready продукт, хотя фактически речь о портфолио vertical slice.

Контрмеры:

- в `09_mvp_scope_timeline.md` разделить 48h vertical slice и 80–120h стабильную версию;
- What-if и P1-функции резать первыми;
- DoD версии 1.5 держать на уровне демонстрируемого MVP, а не коммерческого релиза.

## Риски разработки

### R-6. Старый код слишком завязан на MySQL

Контрмеры:

- единый SQLite слой;
- поэтапная миграция;
- grep checklist;
- не пытаться чинить MySQL runtime.

### R-7. UI завязан на “игрока”

Контрмеры:

- заменить player selector на scope selector;
- сохранить player как demo entity_type;
- не ломать Chart.js pipeline без необходимости.

### R-8. Не хватит 48 часов

Контрмеры:

- резать P1/P2/P3;
- не трогать то, что работает и не мешает P0;
- сначала сделать рабочий vertical slice.

### R-9. Демо-данные окажутся слабее продукта

Контрмеры:

- сделать демо специально под 4 шаблона;
- не пытаться имитировать “настоящую игру целиком”;
- показать 2–3 явные проблемы баланса.

## Допущения

- Пользователь понимает смысл своих игровых данных.
- Первый формат событий — JSONL.
- Первый режим — local-only.
- SQLite достаточно для портфолио-MVP.
- Сложные интеграции не нужны для демонстрации ценности.
- Сценарный анализ версии 1.5 ограничен.
- Демо-данные могут быть синтетическими, если это честно описано.

## Зафиксированные уточнения

- Пользовательские формулы не входят в BalanceCraft 1.5. MVP использует формулы шаблонов и snapshots расчётов.
- `confidence_status` — rule-based статус, а не вероятность. Алгоритм присвоения описан в `05_what_if_levels.md`.
- Analysis coverage в P0 считается на лету через backend API; кэширование в `analysis_coverage_cache` — P1 и только при подтверждённой необходимости.
- Нормализованный ROI доступен только при наличии сопоставимых единиц или явных `cost_value/result_value/value_unit`.
- 48 часов — лимит на портфолио vertical slice, а не реалистичная оценка стабильного внешнего релиза.
- P0 использует четыре встроенных шаблона: Flow Balance, Stock Dynamics, Conversion Efficiency и Operation Intensity.
- P0-параметры могут приходить из demo seed или уже существующих `entity_parameters`; полноценный JSON/CSV import параметров — P1.
- Минимальный What-if обязателен для BalanceCraft 1.5: Level 1 impact estimate + один узкий детерминированный Level 2 сценарий с одним parameter override, явным правилом пересчёта и обязательным `confidence_status`.
- Встроенные template definitions живут в code registry; воспроизводимость расчёта обеспечивается snapshots в БД.
- Demo project — `Demo Forge`; целевой объём — 200–500 событий, 10 observations, 4 P0 bindings/templates и один подготовленный What-if сценарий.

Эти вопросы не блокируют BalanceCraft 1.5 и возвращаются только при переходе к соответствующему scope.

## Главный технический риск

Самая опасная ошибка — начать переписывать всё сразу.

Правильный vertical slice:

```text
SQLite schema
→ import one JSONL
→ profile data
→ bind one template
→ calculate metric values
→ draw chart
→ show one insight
```
