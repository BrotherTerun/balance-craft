# 06. Пользовательский сценарий и UX-логика

## Главный UX-принцип

Пользователь должен получить полезный результат до того, как столкнётся с полной сложностью системы.

Сложные сущности, параметры, сценарии, зависимости и расширенные настройки должны раскрываться постепенно.

## Базовый сценарий первого запуска

```text
запуск приложения
→ экран проектов
→ открыть демо-проект
→ увидеть готовый график
→ открыть карту данных
→ открыть мастер семантики
→ увидеть, как поля связаны с метриками
→ открыть What-if
→ изменить один параметр
→ увидеть сценарную линию
```

Демо-проект обязателен. Без него продукт слишком тяжело объяснять с первого взгляда.

## Сценарий локального анализа

```text
создать проект
→ выбрать папку с JSONL
→ импортировать события
→ получить отчёт импорта
→ увидеть карту данных
→ выбрать шаблон анализа
→ связать переменные шаблона с полями
→ сохранить конфигурацию
→ рассчитать метрики
→ открыть dashboard
→ посмотреть графики и выводы
```

## Сценарий параметрического What-if

```text
импортировать события
→ импортировать или создать параметры
→ настроить семантику
→ выбрать метрику/шаблон
→ открыть What-if
→ выбрать параметр
→ изменить значение
→ пересчитать сценарий
→ сравнить историю и сценарий
→ увидеть статус уверенности
```

## Сценарий повторного анализа нового билда

```text
открыть проект
→ импортировать новый набор событий
→ указать build_id или получить его из событий
→ пересчитать метрики
→ сравнить текущий билд с прошлым
→ проверить, какие метрики изменились
```

Сравнение билдов может быть P1, но модель данных должна не блокировать эту возможность.

## Основные экраны

### 1. Экран проектов

Функции:

- создать проект;
- открыть проект;
- открыть демо;
- показать последние проекты;
- показать статус последнего импорта.

### 2. Импорт данных

Функции:

- выбрать папку или файл;
- показать найденные файлы;
- запустить импорт;
- показать валидные/битые события;
- показать ошибки по файлам и строкам;
- предложить перейти к карте данных.

### 3. Карта данных

Функции:

- список `event_type`;
- количество событий каждого типа;
- список `attributes`;
- типы значений;
- примеры;
- числовые диапазоны;
- предупреждения о грязных данных.


### 3.1. Покрытие анализа

После импорта и настройки семантики интерфейс должен показывать, какие проблемы баланса можно проверить по текущим данным.

Пример блока:

```text
По текущим данным можно анализировать:
✓ баланс потоков
✓ эффективность конверсии
✓ плато прогрессии
✓ волатильность

Нельзя уверенно анализировать:
× бутылочные горлышки — нет событий operation_blocked/action_blocked
× мёртвый контент — нет событий content_used/action_completed
× pacing наград — нет reward-событий с timestamp
```

Функции:

- сопоставить найденные события и semantic bindings с проблемами баланса;
- показать поддерживаемые и неподдерживаемые классы анализа;
- объяснить, каких событий или полей не хватает;
- не блокировать базовый анализ, если часть проблем проверить нельзя.

Этот блок нужен не как отдельный сложный экран, а как честная диагностика возможностей текущего набора данных.

### 4. Мастер семантики

Шаги:

1. Проверка найденных данных.
2. Выбор шаблона анализа.
3. Проверка формул.
4. Связь переменных с полями.
5. Названия метрик.
6. Обзор и сохранение.

Текущий прототип уже имеет близкий wizard. Его нужно сохранить как направление, но убрать жёсткую привязку к игрокам/сессиям и RPG-терминам.

### 5. Dashboard

Функции:

- выбор среза анализа;
- выбор группировки;
- графики метрик;
- карточки выводов;
- предупреждения о качестве данных;
- переход к What-if.

Старый selector “Игрок” заменяется на универсальный selector:

```text
срез анализа → группировка → конкретная сущность, если нужно
```

### 6. What-if panel

Функции:

- список доступных параметров;
- изменение значений;
- запуск сценария;
- сценарные линии на графике;
- выводы по сценарию;
- статус уверенности;
- сброс сценария.

## Empty states

| Ситуация | Сообщение должно объяснять |
|---|---|
| нет проектов | как открыть демо или создать проект |
| нет импортированных событий | как выбрать источник данных |
| нет числовых полей | почему метрики нельзя посчитать |
| не настроена семантика | какие переменные нужно связать |
| проблема баланса не покрыта данными | каких событий, полей или параметров не хватает |
| недостаточно данных | сколько точек нужно для анализа |
| нет параметров для What-if | как импортировать или определить параметры |

## Ошибки

Ошибки должны быть человеческими.

Плохой вариант:

```text
KeyError: attributes.amount
```

Хороший вариант:

```text
В части событий не найдено поле attributes.amount.
Метрика “Чистый поток” рассчитана только по событиям, где это поле есть.
Проверьте карту данных или выберите другое поле в мастере семантики.
```

## UX-правило для MVP

В версии 1.5 важнее понятный линейный путь, чем богатый интерфейс.

Приоритет:

1. демо-проект;
2. понятный импорт;
3. карта данных;
4. Binding Wizard;
5. графики;
6. выводы;
7. покрытие анализа;
8. простой What-if.
