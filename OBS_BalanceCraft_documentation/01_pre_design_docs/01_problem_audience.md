# 01. Problem statement, гипотеза и целевая аудитория

## Problem statement

Инди-разработчикам и небольшим командам сложно анализировать числовой баланс игры, потому что доступные аналитические инструменты чаще закрывают маркетинг, retention, монетизацию и общее поведение игроков, а не внутренние зависимости игровых систем: ресурсы, прогрессию, стоимость действий, ограничения, эффективность операций и нестабильность экономики.

На практике баланс часто проверяется вручную: через Excel, логи, разрозненные графики, субъективные ощущения плейтестеров и одноразовые скрипты. Этот подход работает на ранних прототипах, но быстро разваливается, когда появляются несколько ресурсов, разные режимы, версии билдов, долгие циклы прогрессии и параметры, влияющие друг на друга.

## Гипотеза

Если дать разработчику локальный инструмент, который импортирует игровые события, показывает структуру данных, позволяет вручную назначать им смысл, рассчитывает универсальные метрики баланса и поддерживает простой параметрический What-if, то разработчик сможет быстрее находить проблемы числового баланса без отдельного аналитика и без тяжёлой серверной инфраструктуры.

## Какие проблемы баланса ищет BalanceCraft

BalanceCraft ищет измеримые симптомы проблем баланса. Система не ставит игре абсолютный диагноз “хорошо сбалансировано / плохо сбалансировано”: интерпретация зависит от контекста проекта, целей разработчика и корректности семантических привязок.

| Проблема | Проявление в данных | Почему важно | Что нужно в данных |
|---|---|---|---|
| Дефицит | расход стабильно выше дохода | игрок блокируется или вынужден гриндить | доходы, расходы, запас |
| Профицит | доход стабильно выше расхода | ресурс теряет смысл | доходы, расходы, запас |
| Инфляция | запас растёт быстрее расходов | цены и лимиты перестают работать | запас ресурса по окнам |
| Недостаточные sink-механики | ресурс накапливается, но трат мало или они редкие | экономика перестаёт выводить ресурс из системы | источники и траты ресурса |
| Бутылочное горлышко | один ресурс, параметр или лимит чаще других блокирует операции | прогресс упирается в одну точку | события блокировки, требования |
| Плато прогрессии | прирост падает к нулю | развитие перестаёт ощущаться | метрика прироста по окнам |
| Скачок прогрессии | прирост резко выше соседних участков | игрок перескакивает этапы баланса | прирост силы, уровня, доступа или другого целевого значения |
| Перегретая конверсия | малые затраты дают большой результат | один путь развития доминирует | стоимость и результат действия |
| Низкая конверсия | большие затраты дают слабый результат | действие кажется бесполезным | стоимость и результат действия |
| Доминирующая стратегия | один тип действия, апгрейда или маршрута даёт лучший результат за цену | игроки игнорируют альтернативы | тип действия, стоимость, результат, контекст |
| Мёртвый контент | объект, действие или опция почти не используется либо даёт слабую отдачу относительно стоимости | часть системы фактически не работает | usage-события, стоимость, результат |
| Недоступность операций | много попыток блокируется требованиями | система выглядит закрытой или нечестной | попытки, причины блокировки |
| Неровный pacing наград | награды приходят слишком редко, слишком часто или неравномерно | игрок теряет ощущение ритма и предсказуемости | timestamp, reward-события |
| Волатильность | резкие скачки метрик | баланс плохо предсказуем | временные ряды метрик |
| Нестабильность | близкие состояния расходятся | малые изменения ломают систему | несколько метрик по окнам |

Набор проблем не является закрытым. Для MVP приоритет имеют симптомы, которые можно обнаружить по событиям, параметрам, временным рядам и семантическим привязкам без полноценной симуляции поведения игрока.

## Основная ЦА

### Соло-разработчики и микро-команды

Нужны: быстрый локальный анализ, графики без SQL, импорт файлов, демо-режим, низкий порог входа.

### Technical game designers

Нужны: проверка изменений цен/наград, шаблоны метрик, сравнение билдов, сценарная проверка параметров.

### Начинающие геймдизайнеры

Нужны: понятная связь “события → метрики → выводы”, готовые шаблоны, объяснение основания вывода.

## Ограничения ЦА

| Ограничение                   | Следствие для продукта                                                 |
| ----------------------------- | ---------------------------------------------------------------------- |
| Нет бюджета на аналитику      | Local Mode важнее облака                                               |
| Нет выделенного аналитика     | ошибки и выводы должны быть человеческими                              |
| Нет времени на инфраструктуру | без MySQL, Docker, серверов и админских прав для базового сценария     |
| Данные грязные                | нужна диагностика по файлам, строкам, типам и пропущенным полям        |
| Игры разные                   | ядро не строится исключительно вокруг игроков, предметов или жанров    |
| Нужен быстрый результат       | обязателен демо-проект и короткий путь до первого графика              |
| Не все данные логируются      | система должна показывать, какие проблемы можно проверить, а какие нет |

## Jobs To Be Done

| Ситуация | Пользователь хочет | Чтобы |
|---|---|---|
| После плейтеста | импортировать логи и увидеть динамику | понять, где экономика ломается |
| После изменения цен | сравнить сценарий с историей | не сломать прогрессию |
| При добавлении ресурса | проверить приход, расход и накопление | избежать инфляции, дефицита или бесполезного ресурса |
| При настройке апгрейдов | измерить эффективность конверсии | не сделать один путь доминирующим |
| При появлении жалоб на гринд | проверить bottleneck, pacing наград и блокировки | понять, что именно тормозит прогресс |
| При ревизии контента | увидеть редко используемые действия или объекты | не поддерживать мёртвые элементы системы вслепую |
| При подготовке портфолио | открыть демо и показать график | доказать практическую ценность |
