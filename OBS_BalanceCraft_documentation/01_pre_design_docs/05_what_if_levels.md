# 05. Уровни What-if анализа

## Зачем нужен этот раздел

What-if легко превратить в обещание “симулировать любую игру”. Это опасно: по сырым логам нельзя автоматически и надёжно понять, как произвольный параметр влияет на произвольное поведение игрока.

Поэтому сценарный анализ в BalanceCraft делится на уровни. Каждый уровень должен честно показывать, что именно пересчитывается и насколько результату можно доверять.

## Проблема старого подхода

Слабый What-if меняет производные сигналы:

- средний доход;
- средний расход;
- средний урон;
- среднюю длительность;
- математическое ожидание потока.

Это даёт визуальный прогноз, но плохо отвечает на главный вопрос разработки:

```text
Какой реальный параметр игры нужно изменить?
```

Целевой What-if должен работать с параметрами сущностей:

- цена;
- награда;
- шанс;
- лимит;
- множитель;
- кулдаун;
- стартовое значение;
- штраф;
- бонус.

## Общая логика сценария

```text
выбрать параметр
→ задать override
→ понять, какие события/метрики он может затронуть
→ пересчитать доступный уровень модели
→ сравнить историю и сценарий
→ показать степень уверенности
```

Исторические raw-события не изменяются.

## Level 1 — Оценка влияния параметра

### Смысл

Система показывает, какие события, поля и метрики потенциально связаны с выбранным параметром.

Это не симуляция, а диагностический слой.

### Что можно сделать

- Показать, где параметр используется.
- Показать связанные event_type и attributes.
- Показать метрики, которые могут измениться.
- Предупредить, если связи не подтверждены.

### Пример

```text
Параметр upgrade_cost связан с событиями upgrade_attempt и resource_spent.
Метрики “Доля расхода” и “Стоимость результата” могут измениться.
```

### Статус уверенности

`оценка потенциального влияния`

### Входит в MVP 1.5

Да.

## Level 2 — Контрфактический пересчёт

### Смысл

Система пересчитывает исторические события так, как если бы параметры были другими, но последовательность событий остаётся прежней.

Формула уровня:

```text
Что было бы при той же истории игры, если бы значения параметров были другими?
```

### Ограничение

Поведение игрока считается неизменным. Если цена выросла, система не может сама знать, отказался бы игрок от покупки или пошёл бы фармить больше.

### Что можно сделать

- Пересчитать стоимость действия.
- Пересчитать результат операции.
- Пересчитать доступность, если правило известно.
- Пересчитать метрики поверх изменённых значений.

### Статус уверенности

- `точный пересчёт`, если связь формальная и полная;
- `приближённый пересчёт`, если часть логики упрощена;
- `недостаточно модели`, если нет правила пересчёта.

### Входит в MVP 1.5

Частично. Только простые параметрические сценарии.

## Level 3 — Модельная симуляция

### Смысл

Пользователь явно задаёт модель зависимостей: параметры, формулы, переходы состояний, правила доступности и ограничения.

После этого BalanceCraft может симулировать сценарии внутри заданной модели.

### Что требуется

- dependency rules;
- правила изменения состояния;
- явные связи parameter → event signal → metric;
- сценарный движок;
- сохранение и версия модели.

### Статус уверенности

Зависит от полноты пользовательской модели.

### Входит в MVP 1.5

Нет.

## Level 4 — Внешняя симуляция игры

### Смысл

BalanceCraft не симулирует игру сам. Он передаёт параметры во внешний симулятор или тестовую сборку, получает новые события и анализирует результат.

```text
BalanceCraft задаёт параметры
→ игра/симулятор прогоняет сценарий
→ генерирует новые события
→ BalanceCraft импортирует и сравнивает результат
```

### Что требуется

- API или CLI для запуска симуляции;
- adapter layer;
- сценарные конфиги;
- повторяемые seed-ы;
- импорт результатов как отдельного scenario_run.

### Входит в MVP 1.5

Нет.

## Статусы уверенности

| Статус | Когда показывать |
|---|---|
| Точный пересчёт | есть прямое правило и все нужные данные |
| Приближённый пересчёт | есть правило, но часть поведения упрощена |
| Оценка потенциального влияния | есть связь параметра с событиями/метриками, но нет пересчёта |
| Недостаточно модели | нет dependency rule или формулы влияния |
| Недостаточно данных | мало событий, нет числовых полей, слишком короткий ряд |

## Правила присвоения `confidence_status`

`confidence_status` — это не вероятность и не математическая гарантия. Это rule-based классификация того, насколько сценарный результат опирается на явные данные и правила пересчёта.

| Technical value | UI-лейбл | Когда ставится |
|---|---|---|
| `exact_recalc` | точный пересчёт | есть формальная связь parameter → event/metric, все нужные поля связаны, сценарий не меняет последовательность событий |
| `approx_recalc` | приближённый пересчёт | правило пересчёта есть, но часть поведения или входных данных упрощена; историческая последовательность событий сохраняется |
| `impact_estimate` | оценка потенциального влияния | параметр связан с событиями или метриками, но нет правила пересчёта значений |
| `insufficient_model` | недостаточно модели | нет dependency rule, формулы влияния или связи parameter → metric |
| `insufficient_data` | недостаточно данных | не хватает событий, числовых полей, параметров, observations или ряд слишком короткий |

Минимальное правило для MVP:

```text
есть parameter override + есть binding + есть формула пересчёта + не меняется sequence событий
→ exact_recalc

есть parameter override + есть binding + формула частичная или использует допущения
→ approx_recalc

есть parameter override + есть связь parameter/event/metric, но нет формулы
→ impact_estimate

нет связи или dependency rule
→ insufficient_model

нет данных для проверки
→ insufficient_data
```

Статус должен сохраняться в `scenario_results` и показываться в UI рядом со сценарной линией.

## Связь What-if с проблемами баланса

Не каждая проблема из таксономии баланса одинаково подходит для сценарного анализа. What-if должен показывать уровень уверенности и не обещать пересчёт там, где нет модели зависимости.

| Проблема | Что можно сделать в MVP | Когда нужен более высокий уровень |
|---|---|---|
| Дефицит / профицит | изменить доход или расход и пересчитать поток | если поведение игрока должно измениться из-за новых цен |
| Инфляция | изменить источники, траты или запас и сравнить динамику | если нужны новые действия игроков при изменении экономики |
| Недостаточные sink-механики | проверить усиление существующих трат | если добавляется новый sink, которого не было в истории |
| Бутылочное горлышко | показать параметры и события, связанные с блокировкой | если нужно предсказать обходное поведение игрока |
| Плато / скачок прогрессии | пересчитать известный прирост при изменении параметра | если темп прохождения должен измениться |
| Конверсия | изменить cost/result и пересчитать эффективность | если игроки начнут выбирать другие альтернативы |
| Доминирующая стратегия | оценить разницу эффективности альтернатив | для точного прогноза выбора нужна модель поведения |
| Мёртвый контент | показать usage и отдачу относительно стоимости, проверить изменение параметров | чтобы предсказать рост использования, нужна внешняя или пользовательская модель |
| Неровный pacing наград | изменить размер/частоту известных reward-событий | если меняется расписание появления событий |
| Волатильность / нестабильность | сравнить ряды и сценарные изменения | для причинного прогноза нужна модель зависимостей |

Правило: если изменение параметра может изменить саму последовательность событий, MVP показывает только оценку влияния или приближённый пересчёт, а не точную симуляцию.

## MVP-правило

Для BalanceCraft 1.5 нельзя обещать “симуляцию экономики”. Корректная формулировка:

```text
Простой параметрический What-if с явным уровнем уверенности.
```
