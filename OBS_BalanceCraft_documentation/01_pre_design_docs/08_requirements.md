# 08. Функциональные и нефункциональные требования

## Формат требований

Каждое требование имеет:

- ID;
- компонент;
- приоритет;
- описание;
- критерий готовности.

Приоритеты:

| Приоритет | Значение |
|---|---|
| P0 | обязательно для BalanceCraft 1.5 |
| P1 | желательно для портфолио-версии |
| P2 | после MVP |
| P3 | будущие версии |

# 1. BalanceCraft Desktop

## D-FR-1. Управление проектами

Приоритет: P0

Desktop должен позволять создать проект, открыть проект, открыть демо-проект, показать последние проекты и сохранить настройки проекта.

Критерий готовности:

- новый проект создаётся без ручного SQL;
- проект открывается после перезапуска приложения;
- демо-проект доступен с первого экрана.

## D-FR-2. Локальное хранилище

Приоритет: P0

Desktop должен автоматически создавать SQLite-БД в пользовательской папке BalanceCraft.

Критерий готовности:

- приложение запускается без MySQL;
- база создаётся автоматически;
- пользователю не нужны root-пароли, службы Windows или админские права.

## D-FR-3. Импорт JSONL

Приоритет: P0

Desktop должен импортировать локальные JSONL-файлы событий.

Критерий готовности:

- можно выбрать папку с `.jsonl`;
- система находит файлы;
- валидирует события;
- показывает количество найденных, валидных и импортированных событий;
- ошибки содержат файл и строку.

## D-FR-4. Профилирование данных

Приоритет: P0

После импорта система должна строить карту данных.

Критерий готовности:

- показаны `event_type` и количество событий;
- показаны поля `attributes`;
- показаны типы, частоты, примеры и числовые диапазоны;
- грязные поля отмечены предупреждениями.

## D-FR-5. Мастер семантики

Приоритет: P0

Desktop должен позволять вручную связывать переменные шаблона с полями событий.

Критерий готовности:

- пользователь выбирает шаблон;
- выбирает поля для переменных;
- выбирает event_type-фильтры;
- выбирает агрегацию;
- задаёт названия метрик;
- сохраняет конфигурацию в проекте.

## D-FR-6. Шаблоны анализа

Приоритет: P0

Desktop должен поддерживать минимум четыре универсальных шаблона:

1. Баланс потоков.
2. Динамика запаса.
3. Эффективность конверсии.
4. Интенсивность операций.

P1-шаблоны расширяют покрытие проблем баланса:

1. Давление стоимости.
2. Доступность действий.
3. Использование контента.
4. Ритм наград.

Критерий готовности:

- каждый шаблон имеет переменные, формулы, названия метрик и описание;
- шаблоны не требуют RPG-сущностей;
- формулы используют явную политику `safe_div` / `N/A` для нулевых знаменателей;
- метрики не смешивают несопоставимые единицы без явной нормализации.

## D-FR-7. Расчёт метрик

Приоритет: P0

Метрики должны рассчитываться по сохранённым semantic bindings.

Критерий готовности:

- raw-события не изменяются;
- результат сохраняется как отдельный metric run;
- расчёт можно повторить без повторного импорта;
- значения, которые нельзя корректно посчитать, возвращаются как `N/A` или warning, а не как искусственно подставленные числа.

## D-FR-8. Аналитические срезы

Приоритет: P0

Desktop должен анализировать данные не только по “игроку”, а по универсальным срезам.

Минимальные срезы:

- весь проект;
- `entity_id`;
- `observation_id`;
- `observation_type`;
- `event_type`;
- `build_id`, если есть.

Критерий готовности:

- selector “Игрок” заменён или абстрагирован до “Срез анализа”.

## D-FR-9. Визуализация

Приоритет: P0

Desktop должен строить графики рассчитанных метрик.

Критерий готовности:

- график строится после расчёта;
- можно отобразить несколько метрик;
- подписи берутся из конфигурации проекта;
- пустые состояния объясняют проблему.

## D-FR-10. Практические выводы

Приоритет: P0

Desktop должен показывать выводы по рассчитанным рядам.

Критерий готовности:

- каждый вывод имеет уровень важности;
- текст “что обнаружено”;
- рекомендацию;
- основание вывода;
- связанные метрики.

## D-FR-11. What-if

Приоритет: P0/P1

Desktop должен поддерживать простой параметрический What-if без изменения истории.

Критерий готовности:

- можно выбрать параметр;
- изменить значение;
- построить сценарную линию;
- увидеть статус уверенности;
- статус уверенности определяется по правилам из `05_what_if_levels.md`;
- raw-события не изменяются.


## D-FR-12. Покрытие анализа

Приоритет: P0 для базовой проверки на лету, P1 для расширенного покрытия и кэша

Desktop должен показывать, какие проблемы баланса можно проверить по текущему набору данных и semantic bindings.

Критерий готовности для P0:

- система определяет, можно ли проверить базовые проблемы P0: дефицит, профицит, инфляцию, плато, перегретую/низкую конверсию;
- если нужных событий или полей нет, интерфейс показывает причину;
- отсутствие данных для одной проблемы не блокирует анализ других проблем.

Критерий готовности для P1:

- система показывает покрытие для бутылочных горлышек, мёртвого контента, pacing наград, недоступности операций и недостаточных sink-механик;
- результат покрытия может кэшироваться, но кэш не является обязательным для P0.

## D-FR-13. Анализ расширенных симптомов баланса

Приоритет: P1/P2

Desktop должен постепенно расширять анализ за пределы базовых потоков и прогрессии.

P1-симптомы:

- недостаточные sink-механики;
- бутылочные горлышки;
- скачки прогрессии;
- мёртвый контент;
- неровный pacing наград;
- недоступность операций.

P2-симптомы:

- доминирующие стратегии;
- сравнение альтернативных путей развития;
- расширенная нестабильность на нескольких рядах.

Критерий готовности:

- каждый поддержанный симптом связан с шаблоном анализа;
- каждый вывод содержит основание вывода;
- неподдержанные симптомы явно помечаются как недоступные для текущей версии или текущих данных.

## D-FR-14. Корректность расчёта метрик

Приоритет: P0

Desktop должен рассчитывать метрики так, чтобы формулы не создавали ложную точность.

Критерий готовности:

- деление на ноль или почти нулевой знаменатель возвращает `N/A` или warning;
- пользователь видит, если метрика не рассчитана из-за отсутствующих данных;
- ROI рассчитывается только для сопоставимых единиц или явно нормализованных значений;
- если нормализации нет, UI использует формулировки “результат на единицу затрат” или “стоимость единицы результата”, а не строгий ROI;
- пороги плато, скачков и волатильности хранятся как настройки шаблона или явно отображаются в описании расчёта;
- calculation warnings сохраняются вместе с metric run или возвращаются в API.

## D-FR-15. Нормализация ценности для ROI

Приоритет: P1

Desktop может поддерживать value normalization profile для случаев, когда пользователь хочет сравнивать стоимость и результат в общей дизайнерской шкале.

Критерий готовности:

- пользователь может указать, какие поля являются `cost_value`, `result_value` и `value_unit`;
- если такие поля есть во входных данных, система может считать нормализованный ROI;
- если таких полей нет, система не называет отношение разных единиц строгим ROI;
- профиль нормализации сохраняется в проекте и может быть использован metric run;
- изменение профиля нормализации не меняет raw-события.

## D-FR-16. Пользовательские формулы

Приоритет: P2

Пользовательский редактор формул не входит в BalanceCraft 1.5. В MVP пользователь настраивает semantic bindings, labels, filters и aggregations, но не пишет произвольные формулы.

Критерий готовности для 1.5:

- формулы берутся из шаблонов анализа;
- metric run сохраняет snapshot формул шаблона;
- UI не обещает произвольный formula editor;
- если пользовательские формулы появятся в будущей версии, они должны использовать ограниченный expression language, `safe_div`, валидацию переменных и calculation warnings.

# 2. Нефункциональные требования Desktop

## D-NFR-1. Local-first

Приоритет: P0

Приложение должно работать без сервера, интернета, регистрации и внешней СУБД.

## D-NFR-2. Простота запуска

Приоритет: P0

Целевой сценарий:

```text
скачал
→ запустил
→ открыл демо
→ увидел пользу
```

## D-NFR-3. Модульность

Приоритет: P0

Код должен разделять:

- импорт;
- хранение;
- профилирование;
- семантику;
- расчёт;
- визуализацию;
- insights;
- what-if.

## D-NFR-4. Человеческая диагностика

Приоритет: P0

Ошибки должны объяснять, что произошло и что делать дальше.

## D-NFR-5. Производительность

Приоритет: P1

Ориентиры:

- до 100 000 событий — комфортно;
- до 1 000 000 событий — допустимо с индексацией и progress UI;
- больше — через агрегаты или серверный экспорт.

# 3. Требования к БД

Требования к БД относятся к BalanceCraft Desktop. В версии 1.5 БД не является отдельным серверным компонентом: это локальное SQLite-хранилище проекта.

## DB-FR-1. SQLite runtime

Приоритет: P0

SQLite — единственная runtime-БД Desktop 1.5.

Критерий готовности:

- приложение не требует MySQL, PostgreSQL, Docker или отдельной службы;
- БД создаётся автоматически при первом запуске или создании проекта;
- путь к БД выбирается приложением без ручной настройки пользователя;
- подключение к БД проходит через единый db layer.

## DB-FR-2. Инициализация схемы

Приоритет: P0

DB layer должен создавать минимальную схему проекта без ручного SQL.

Критерий готовности:

- при отсутствии БД создаются таблицы базового P0-набора;
- приложение не падает при повторном запуске init;
- ошибки создания схемы показываются как человеческая диагностика;
- в схеме нет MySQL-specific SQL.

## DB-FR-3. Версионирование и миграции

Приоритет: P1

Схема должна иметь версию и механизм обновления.

Критерий готовности:

- есть таблица или иной механизм `schema_migrations`;
- каждая миграция имеет номер, имя и дату применения;
- повторное применение уже выполненной миграции не ломает БД;
- при несовместимой версии приложение показывает понятную ошибку.

## DB-FR-4. Raw events отдельно от производных данных

Приоритет: P0

Raw-события не изменяются при расчёте метрик, сценариев или повторной настройке semantic bindings.

Критерий готовности:

- `events.attributes_json` хранит исходные attributes без потери данных;
- metric runs сохраняются отдельно от events;
- scenario results сохраняются отдельно от metric values;
- пересчёт метрик не меняет импортированные события.

## DB-FR-5. Проекты и изоляция данных

Приоритет: P0

Все ключевые таблицы должны быть привязаны к `project_id`.

Критерий готовности:

- события, параметры, bindings, metric runs и scenarios относятся к конкретному проекту;
- данные одного проекта не попадают в выборки другого проекта;
- удаление/закрытие проекта не требует ручной очистки БД;
- recent projects и настройки проекта не смешиваются с raw events.

## DB-FR-6. Import runs и трассировка источника

Приоритет: P0

Импорт должен сохранять происхождение данных.

Критерий готовности:

- для каждого импорта создаётся `import_run`;
- для каждого файла сохраняется `source_file`;
- событие хранит ссылку на import run, source file и номер строки;
- отчёт импорта можно восстановить после перезапуска приложения.

## DB-FR-7. Индексы для базовых срезов

Приоритет: P0

БД должна иметь индексы для основных операций dashboard, data profiling и metric engine.

Минимальные индексы:

- `events.project_id`;
- `events.entity_id`;
- `events.observation_id`;
- `events.event_type`;
- `events.timestamp`;
- `events.build_id`;
- `metric_values.metric_run_id`;
- `metric_values.metric_key`;
- `entity_parameters.project_id`;
- `entity_parameters.entity_id`;
- `entity_parameters.parameter_key`.

Критерий готовности:

- dashboard не делает полные сканы без необходимости на типовых запросах;
- импорт 100 000 событий остаётся пригодным для интерактивной работы;
- индексы описаны в schema-файле или миграциях.

## DB-FR-8. Хранение semantic bindings

Приоритет: P0

БД должна хранить настройки связи данных с переменными шаблонов.

Критерий готовности:

- binding сохраняет template key, variable key, source kind, source path, event filters и aggregation;
- binding можно переиспользовать после перезапуска;
- metric run сохраняет snapshot binding, чтобы старые результаты не менялись после правки конфигурации;
- binding не требует жанровых таблиц вроде players/items/skills.

## DB-FR-9. Хранение metric runs и warnings

Приоритет: P0

Результаты расчёта должны хранить не только числовые значения, но и статус корректности.

Критерий готовности:

- `metric_runs` хранит статус, warnings и snapshot формул;
- `metric_values` поддерживает status для `ok`, `n/a`, `warning`, `error`;
- calculation warnings сохраняются или возвращаются через API;
- значения, которые нельзя корректно посчитать, не подменяются искусственными числами.

## DB-FR-10. Параметры и сценарии

Приоритет: P0/P1

БД должна поддерживать хранение параметров сущностей и сценарных override-ов для What-if.

Критерий готовности:

- параметры хранятся отдельно от событий;
- параметр имеет entity_id, parameter_key, value, value_type и build_id, если он доступен;
- сценарий хранит base metric run и список overrides;
- сценарные результаты не изменяют исторические metric values;
- value normalization profile, если используется, хранится отдельно от raw-событий и metric values.

## DB-FR-11. Покрытие анализа

Приоритет: P0 для backend API, P1 для кэширования в БД

БД или backend API должны поддерживать результат проверки analysis coverage.

Критерий готовности:

- система может вернуть список проблем баланса со статусом `available`, `partially_available`, `missing_data` или `unsupported_in_version`;
- для `missing_data` возвращается список недостающих событий, полей или параметров;
- для P0 результат можно считать на лету;
- для P1 результат можно кэшировать в БД;
- отсутствие покрытия по одной проблеме не блокирует другие шаблоны.

## DB-NFR-1. Отказ от внешних зависимостей

Приоритет: P0

Работа с БД не должна требовать установки внешней СУБД, запуска служб или прав администратора.

## DB-NFR-2. Целостность

Приоритет: P0

DB layer должен использовать транзакции для импорта и расчёта.

Критерий готовности:

- частично упавший импорт не оставляет проект в невалидном состоянии;
- foreign keys включены через `PRAGMA foreign_keys = ON`;
- ошибки транзакций возвращаются в отчёт, а не теряются в консоли.

## DB-NFR-3. Переносимость

Приоритет: P1

Файл БД должен быть переносимым как часть локального проекта.

Критерий готовности:

- проект можно скопировать вместе с БД и открыть на другой машине с совместимой версией приложения;
- абсолютные пути к исходным файлам не являются единственным способом понять историю импорта;
- source files могут хранить и путь, и имя, и hash.

# 4. Требования к интерфейсу

## UI-FR-1. Линейный путь первого результата

Приоритет: P0

Интерфейс должен вести пользователя от проекта к импорту, карте данных, семантике, графикам и выводам.

Критерий готовности:

- на первом экране есть путь к demo project;
- после импорта пользователь получает следующий рекомендуемый шаг;
- без настройки всех расширенных параметров можно получить первый график;
- пользователь не должен знать SQL или структуру БД.

## UI-FR-2. Экран проектов

Приоритет: P0

Интерфейс должен позволять создать проект, открыть проект и открыть демо.

Критерий готовности:

- видны последние проекты;
- виден статус последнего импорта, если он есть;
- ошибки открытия проекта объясняются человеком;
- демо-проект доступен без импорта внешних данных.

## UI-FR-3. Импорт данных

Приоритет: P0

Интерфейс должен поддерживать выбор файла или папки с JSONL и показывать результат импорта.

Критерий готовности:

- пользователь видит найденные файлы;
- после импорта видит количество строк, валидных событий, ошибок и предупреждений;
- ошибки содержат файл и строку;
- из отчёта импорта можно перейти к карте данных.

## UI-FR-4. Карта данных

Приоритет: P0

Интерфейс должен показывать структуру импортированных событий без необходимости открывать raw JSON.

Критерий готовности:

- показаны event types и частоты;
- показаны attributes, типы значений, примеры и диапазоны;
- грязные или смешанные поля отмечены предупреждениями;
- пользователь может понять, какие поля можно использовать в Binding Wizard.

## UI-FR-5. Binding Wizard

Приоритет: P0

Интерфейс должен позволять настроить semantic bindings пошагово.

Критерий готовности:

- пользователь выбирает шаблон;
- видит переменные и формулы шаблона;
- выбирает event types, attributes, aggregation и filters;
- видит предупреждения о несовместимых типах;
- сохраняет binding и может вернуться к нему позже.

## UI-FR-6. Dashboard

Приоритет: P0

Интерфейс должен показывать рассчитанные метрики в виде графиков, карточек и таблиц.

Критерий готовности:

- можно выбрать metric run;
- можно выбрать scope анализа;
- график поддерживает несколько метрик;
- `N/A` и warnings не скрываются;
- подписи метрик используют пользовательские названия или названия шаблонов.

## UI-FR-7. Практические выводы

Приоритет: P0

Интерфейс должен показывать выводы так, чтобы было понятно, почему система подсветила проблему.

Критерий готовности:

- каждый вывод имеет уровень важности;
- вывод содержит текст “что обнаружено”;
- вывод содержит рекомендацию;
- вывод содержит основание вывода;
- вывод ссылается на метрики, окна наблюдения или события.

## UI-FR-8. Покрытие анализа

Приоритет: P0/P1

Интерфейс должен показывать, какие проблемы можно проверить по текущим данным.

Критерий готовности:

- виден список доступных и недоступных классов анализа;
- для недоступных проблем указано, каких событий, полей или параметров не хватает;
- неподдержанные в текущей версии проблемы не выглядят как ошибка пользователя;
- coverage не блокирует базовый анализ.

## UI-FR-9. What-if panel

Приоритет: P0/P1

Интерфейс должен поддерживать простой сценарный анализ параметров.

Критерий готовности:

- пользователь выбирает параметр;
- видит исходное значение и новое значение;
- запускает сценарий;
- видит историческую и сценарную линии;
- видит confidence status;
- может сбросить сценарий.

## UI-FR-10. Empty states

Приоритет: P0

Каждое пустое состояние должно объяснять следующий шаг.

Критерий готовности:

- нет проектов → предложить демо или создание проекта;
- нет событий → предложить импорт;
- нет числовых полей → объяснить, почему метрики ограничены;
- нет bindings → предложить открыть мастер семантики;
- нет параметров → объяснить ограничения What-if.

## UI-NFR-1. Прогрессивное раскрытие сложности

Приоритет: P1

Расширенные настройки доступны, но не обязательны для первого анализа.

## UI-NFR-2. Человеческий язык

Приоритет: P0

UI не должен показывать пользователю сырые stack traces как основной текст ошибки.

## UI-NFR-3. Согласованная терминология

Приоритет: P0

Интерфейс использует термины из `11_glossary.md`: project, entity, observation, event, attribute, parameter, metric, binding, scope, scenario.

# 5. SDK Lite

SDK Lite — будущий компонент P2. Требования фиксируются заранее, чтобы формат событий Desktop 1.5 не пришлось менять при появлении SDK.

## SDK-FR-1. TrackEvent

Приоритет: P2

SDK должен предоставлять простой метод записи события.

Критерий готовности:

- разработчик может передать `event_type` и `attributes`;
- SDK добавляет timestamp, если он не передан;
- SDK принимает entity_id и observation_id;
- метод не требует знания внутренней БД Desktop.

## SDK-FR-2. Локальная запись JSONL

Приоритет: P2

SDK должен писать события локально в JSONL-формате, совместимом с Desktop import.

Критерий готовности:

- одна строка соответствует одному событию;
- формат соответствует `12_input_data_formats.md`;
- файл можно импортировать в Desktop без ручной конвертации;
- при ошибке записи SDK не падает вместе с игрой.

## SDK-FR-3. Event envelope

Приоритет: P2

SDK должен формировать стабильную оболочку события.

Минимальные поля:

- `timestamp`;
- `entity_id`;
- `event_type`;
- `attributes`.

Желательные поля:

- `entity_type`;
- `observation_id`;
- `observation_type`;
- `build_id`;
- `schema_version`;
- `source_id`.

Критерий готовности:

- отсутствующие желательные поля не ломают импорт;
- обязательные поля валидируются до записи или помечаются ошибкой SDK;
- attributes остаются пользовательским объектом.

## SDK-FR-4. Буферизация и ограничение кэша

Приоритет: P2

SDK должен ограничивать объём локальных логов.

Критерий готовности:

- можно задать максимальный размер файла или директории логов;
- при переполнении применяется понятная политика: rotation, oldest-first cleanup или остановка записи;
- политика описана в документации SDK;
- SDK не создаёт бесконечно растущий кэш.

## SDK-FR-5. Offline-first поведение

Приоритет: P2

SDK должен корректно работать без сети.

Критерий готовности:

- Local Mode не требует endpoint;
- события продолжают писаться локально;
- отсутствие сети не влияет на игровой процесс;
- отправка на Self-hosted Collector включается только явной настройкой.

## SDK-FR-6. Настройка endpoint для Self-hosted

Приоритет: P3

SDK должен уметь отправлять события на endpoint разработчика игры, если это включено.

Критерий готовности:

- endpoint не захардкожен;
- без endpoint SDK не отправляет события;
- project token/API key задаётся разработчиком игры;
- ошибки отправки не блокируют игровой процесс.

## SDK-FR-7. Batch отправка

Приоритет: P3

SDK должен отправлять события батчами, а не по одному запросу на каждое событие.

Критерий готовности:

- batch size настраивается;
- есть ограничение размера payload;
- неуспешная отправка возвращает события в retry queue или сохраняет локально;
- дубликаты не должны создаваться без необходимости.

## SDK-FR-8. Минимальный Unity SDK

Приоритет: P2

Первый SDK может быть Unity-ориентированным.

Критерий готовности:

- есть пример вызова `TrackEvent`;
- есть пример записи локального JSONL;
- есть пример build_id/schema_version;
- есть минимальная сцена или sample script для проверки.

## SDK-NFR-1. Безопасность по умолчанию

Приоритет: P2

SDK не собирает персональные данные автоматически и не имеет скрытых отправок.

Критерий готовности:

- SDK не собирает email, имя игрока, открытый SteamID, IP или пользовательский текстовый ввод;
- сетевые отправки выключены по умолчанию;
- payload формируется из данных, которые явно передаёт разработчик игры.

## SDK-NFR-2. Неблокирующая работа

Приоритет: P2

SDK не должен заметно влиять на игровой процесс.

Критерий готовности:

- ошибки записи/отправки не приводят к падению игры;
- запись событий не выполняет тяжёлую синхронную операцию на каждый кадр;
- SDK можно отключить конфигом.

## SDK-NFR-3. Совместимость с Desktop

Приоритет: P2

SDK не должен создавать формат событий, который требует отдельного конвертера для Desktop.

# 6. Self-hosted Collector

Self-hosted Collector — будущий компонент P3. Он не входит в BalanceCraft 1.5 и не является сервером авторов BalanceCraft. Это сервер, который разработчик игры разворачивает у себя.

## SHS-FR-1. Batch endpoint

Приоритет: P3

Collector должен принимать батчи событий от SDK.

Критерий готовности:

- endpoint принимает JSON payload с массивом событий;
- каждый batch содержит project token/API key;
- размер запроса ограничен;
- невалидные события возвращают понятную ошибку;
- частично валидный batch обрабатывается по описанной политике.

## SHS-FR-2. Schema validation

Приоритет: P3

Collector должен валидировать базовую схему событий.

Критерий готовности:

- проверяются обязательные поля;
- проверяется, что attributes является object;
- слишком большие payloads отклоняются;
- запрещённые поля могут отбрасываться или блокировать событие;
- ошибки валидации логируются без персональных данных.

## SHS-FR-3. Project isolation

Приоритет: P3

Collector должен разделять данные разных проектов.

Критерий готовности:

- project token/API key определяет проект;
- события одного проекта не экспортируются в другой проект;
- невалидный token отклоняется;
- token не пишется в публичные логи.

## SHS-FR-4. Хранение raw events

Приоритет: P3

Collector должен хранить raw-события до экспорта или истечения retention policy.

Критерий готовности:

- события сохраняются без потери attributes;
- сохраняется время получения на сервере;
- сохраняется статус валидации;
- сырые события можно экспортировать для Desktop.

## SHS-FR-5. Export для Desktop

Приоритет: P3

Collector должен отдавать экспорт в формате, пригодном для Desktop import.

Критерий готовности:

- поддерживается JSONL export;
- желательно поддержать CSV export как P3/P4;
- экспорт можно ограничить по project, build_id и диапазону времени;
- экспорт не содержит IP и служебные серверные данные как analytic payload.

## SHS-FR-6. Retention policy

Приоритет: P3

Collector должен поддерживать удаление старых raw events.

Критерий готовности:

- retention window задаётся конфигом;
- старые события можно удалить вручную или scheduled job;
- удаление не требует ручного SQL;
- политика описана в документации Collector.

## SHS-FR-7. Rate limiting

Приоритет: P3

Collector должен защищаться от слишком частых или слишком больших запросов.

Критерий готовности:

- есть ограничение на размер batch;
- есть ограничение на частоту запросов;
- превышение лимита возвращает понятный статус;
- rate limit не раскрывает лишнюю информацию о сервере.

## SHS-FR-8. Admin/export CLI

Приоритет: P3

Минимальный Collector может не иметь web-интерфейса, но должен иметь простой способ управления экспортом.

Критерий готовности:

- можно запустить экспорт через CLI или простой endpoint;
- можно проверить статус сервера;
- можно очистить старые данные согласно retention;
- документация описывает минимальный workflow.

## SHS-NFR-1. Safe defaults

Приоритет: P3

Collector должен иметь безопасные настройки по умолчанию.

Критерий готовности:

- HTTPS предполагается для production-развёртывания;
- token/API key обязателен;
- schema validation включена;
- rate limiting включён;
- retention policy задана;
- запрещённые поля не экспортируются в Desktop.

## SHS-NFR-2. Развёртывание разработчиком игры

Приоритет: P3

Collector не должен быть обязательной инфраструктурой авторов BalanceCraft.

Критерий готовности:

- документация явно говорит, что сервер принадлежит разработчику игры;
- BalanceCraft Desktop может работать без Collector;
- SDK может работать только в Local Mode;
- отсутствие Collector не ломает MVP.

## SHS-NFR-3. Наблюдаемость без персональных данных

Приоритет: P3

Логи Collector должны помогать диагностировать ошибки без записи лишних персональных данных.

Критерий готовности:

- логи содержат статус, project id/token hash, количество событий и тип ошибки;
- IP не экспортируется как analytic payload;
- payload ошибок не должен сохранять пользовательский текстовый ввод.
