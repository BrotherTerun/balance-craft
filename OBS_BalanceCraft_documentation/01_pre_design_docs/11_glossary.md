# 11. Словарь сущностей

## Назначение

Словарь фиксирует язык проекта. Он нужен, чтобы код, документация, UI и будущая БД не расходились в понятиях.

## Core terms

### Project / проект

Локальный проект анализа в BalanceCraft.

Содержит:

- raw-события;
- параметры;
- настройки импорта;
- semantic bindings;
- metric runs;
- scenarios;
- пользовательские названия метрик;
- snapshots формул шаблонов;
- warnings и основания выводов.

### Entity / сущность

Любой анализируемый или параметризуемый элемент игровой системы.

Сущностью может быть:

- игрок;
- персонаж;
- ресурс;
- предмет;
- операция;
- правило;
- уровень;
- волна;
- билд;
- система;
- произвольный объект пользователя.

`entity` — базовое понятие. “Игрок”, “предмет”, “навык” и подобные термины — только возможные типы сущностей.

### Entity type / тип сущности

Категория сущности.

Примеры:

```text
actor
resource
operation
rule
item
skill
unit
level
system
custom
```

Тип не должен зашиваться в архитектуру как обязательный жанровый объект.

### Event / событие

Атомарная запись о том, что произошло в игре или игровой системе.

Событие может описывать:

- начисление значения;
- расход значения;
- изменение параметра;
- попытку операции;
- успешную операцию;
- блокировку операции;
- применение модификатора;
- изменение состояния.

### Attribute / атрибут события

Произвольное поле внутри `attributes` события.

Пример:

```json
{
  "amount": 10,
  "resource_type": "soft_currency",
  "context": "upgrade"
}
```

BalanceCraft не должен заранее знать, что означает `amount` или `resource_type`.

### Observation / окно наблюдения

Логическое окно анализа.

Может соответствовать:

- игровой сессии;
- уровню;
- забегу;
- бою;
- дню;
- волне;
- главе;
- тестовому прогону;
- произвольному интервалу.

Старое слово “сессия” допускается только как один из типов observation.

### Parameter / параметр

Настройка игровой системы, которая может влиять на события и метрики.

Примеры:

- стоимость;
- награда;
- множитель;
- лимит;
- шанс;
- порог;
- кулдаун;
- скорость восстановления;
- штраф;
- бонус.

### Entity parameter / параметр сущности

Конкретное значение параметра для конкретной сущности.

Пример:

```text
entity_id = upgrade_iron_sword
parameter_key = cost_soft_currency
value = 120
```

### Parameter catalog / справочник параметров

Набор параметров, импортированный или созданный для проекта.

Пример:

- таблица цен апгрейдов;
- таблица наград уровней;
- таблица шансов выпадения;
- таблица лимитов.

### Metric / метрика

Рассчитанный показатель, полученный из событий и/или параметров.

Пример:

- чистый поток;
- доля расхода;
- эффективность конверсии;
- интенсивность операций;
- доля блокировок.

### Metric template / шаблон метрик

Набор переменных, формул и интерпретаций для типового анализа.

Шаблон не должен быть жанровым.

### Metric run / запуск расчёта

Один факт расчёта метрик по конкретной конфигурации.

Нужен, чтобы:

- хранить историю расчётов;
- пересчитывать без потери старых результатов;
- сравнивать настройки.

### Metric value / значение метрики

Конкретное рассчитанное значение метрики для окна наблюдения, сущности, среза или сценария.

### Semantic binding / семантическая привязка

Связь между переменной шаблона и конкретным источником данных.

Пример:

```text
flow_in → events.attributes.amount where event_type = resource_gained
flow_out → events.attributes.amount where event_type = resource_spent
```

### Scope / срез анализа

Правило отбора и группировки данных.

Примеры:

- весь проект;
- конкретная сущность;
- тип сущности;
- observation_type;
- build_id;
- event_type;
- значение конкретного attribute.

### Scenario / сценарий

Набор изменений параметров, применяемых для What-if анализа.

### Scenario override / сценарное изменение

Конкретное изменение параметра внутри сценария.

Пример:

```text
upgrade_cost *= 0.8
reward_amount += 10
cooldown = 5
```

### Scenario result / результат сценария

Рассчитанные метрики и выводы для сценария.

### Основание вывода / evidence

Набор метрик, значений, событий, временных окон или сравнений, на которые ссылается аналитический вывод.

В коде техническое поле может называться `evidence`, но в русском UI и документации используется “основание вывода”. Это не строгое доказательство и не гарантия истинности, а объяснение, почему система подсветила проблему.

### Formula snapshot / снимок формулы

Сохранённая версия формулы шаблона, использованная в конкретном metric run.

Нужен, чтобы старые результаты оставались воспроизводимыми даже после изменения шаблона в будущей версии.

### Пользовательская формула

Произвольная формула, которую пользователь сам задаёт в интерфейсе.

Не входит в BalanceCraft 1.5. Для MVP пользователь настраивает semantic bindings, labels, filters и aggregations, но не пишет произвольные формулы. Если formula editor появится позже, он должен использовать ограниченный expression language, валидацию переменных и безопасные операции вроде `safe_div`.

### Value normalization profile / профиль нормализации ценности

Правило приведения разных игровых величин к общей дизайнерской шкале.

Пример: золото и урон нельзя напрямую подставлять в финансовую формулу ROI. Если пользователь хочет считать нормализованный ROI, он должен предоставить `cost_value`, `result_value` и `value_unit` во входных данных или через отдельный профиль нормализации.

### Confidence status / статус уверенности

Rule-based оценка надёжности сценарного результата.

Это не вероятность и не математическое доказательство. Статус показывает, на каком основании построен сценарный результат.

Возможные значения:

- `exact_recalc` / точный пересчёт;
- `approx_recalc` / приближённый пересчёт;
- `impact_estimate` / оценка потенциального влияния;
- `insufficient_model` / недостаточно модели;
- `insufficient_data` / недостаточно данных.


### SDK Lite

Будущий компонент BalanceCraft для записи событий из игры.

Минимальная роль SDK Lite:

- принять событие от игры;
- добавить технические поля вроде timestamp;
- записать событие в локальный JSONL;
- при наличии явной настройки отправить batch на Self-hosted Collector.

SDK Lite не является обязательной частью BalanceCraft 1.5.

### Self-hosted Collector

Будущий серверный компонент, который разработчик игры разворачивает у себя.

Назначение:

- принимать batch-события от SDK;
- валидировать базовую схему;
- хранить raw events;
- отдавать экспорт для BalanceCraft Desktop.

Self-hosted Collector не является сервером авторов BalanceCraft и не входит в MVP 1.5.

### Batch / батч событий

Группа событий, отправляемая или обрабатываемая одним запросом.

Используется в SDK и Self-hosted Collector, чтобы не отправлять каждое событие отдельным сетевым запросом.

### Project token / API key

Технический ключ проекта для Self-hosted Collector.

Нужен, чтобы Collector понимал, к какому проекту относится batch событий. Не должен попадать в публичные логи или клиентскую документацию как открытый секрет.

### Retention policy

Правило хранения и удаления raw-событий.

Определяет, сколько времени Collector или локальный проект хранит события и когда старые данные должны удаляться или архивироваться.

## Legacy terms

### Player / игрок

Не является фундаментальной сущностью BalanceCraft. Может быть `entity_type = actor/player` в конкретном проекте.

### Session / сессия

Не является фундаментальной сущностью. Может быть `observation_type = session`.

### Item / предмет

Не является фундаментальной таблицей. Может быть `entity_type = item`.

### Skill / навык

Не является фундаментальной таблицей. Может быть `entity_type = skill`.

### XP / опыт

Не является встроенным смыслом. Может быть пользовательским attribute или parameter.
