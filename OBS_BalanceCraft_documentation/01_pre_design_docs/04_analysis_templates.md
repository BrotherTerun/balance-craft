# 04. Шаблоны анализа

## Назначение шаблонов

Шаблон анализа — это не жанровый пресет и не жёстко зашитая метрика. Это описание типовой числовой зависимости, которую можно применить к разным играм через семантические привязки.

Шаблон задаёт:

- какие переменные нужны;
- какие типы событий подходят;
- как агрегировать значения;
- какие метрики считать;
- как интерпретировать результат;
- какие ограничения у вывода.

В коде шаблоны могут иметь английские ID. В интерфейсе и документации используются русские названия.

## Общие правила

1. Шаблон не должен требовать конкретного жанра.
2. Шаблон не должен требовать сущности “игрок”.
3. Любая переменная шаблона должна связываться через Binding Wizard.
4. Формулы должны храниться отдельно от raw-событий.
5. Выводы должны ссылаться на метрики и основание вывода.
6. Если данных недостаточно, шаблон должен возвращать предупреждение, а не уверенный вывод.
7. Если знаменатель формулы равен нулю или почти равен нулю, метрика должна возвращать `N/A` или warning, а не искусственно делить на `1`.

## Статус метрик

Метрики BalanceCraft — это прикладные диагностические агрегаты поверх событийной телеметрии: суммы, разницы, частоты, доли, отношения, интервалы и разбросы. Они не являются “магическими” отраслевыми KPI с единым названием для всех игр.

Их смысл совпадает с распространёнными паттернами игровой аналитики:

- resource/source/sink tracking для экономики ресурсов;
- progression tracking для уровней, миссий, забегов и этапов прохождения;
- custom/design events для уникальных действий конкретной игры;
- dashboards/funnels/data explorer подход для сравнения рядов, событий и группировок.

Поэтому формулы в шаблонах считаются допустимыми для MVP, если выполняются условия:

- пользователь явно связал переменные шаблона с данными;
- единицы измерения понятны или указаны;
- деление на ноль не маскируется;
- метрика показывает ограничение вывода;
- вывод не заявляет причинность там, где есть только корреляция или симптом.

## Нотация формул

| Запись | Значение |
|---|---|
| `Σx` | сумма значений `x` в выбранном окне, срезе или группе |
| `count(x)` | количество событий/строк, где значение `x` присутствует |
| `count_if(condition)` | количество событий, где условие истинно |
| `safe_div(a, b)` | `a / b`, если `b` достаточно велик; иначе `N/A` + warning |
| `Δx` | изменение значения между соседними окнами |
| `Δt` | длительность окна или интервал между событиями |
| `mean(x)` | среднее значение |
| `median(x)` | медиана |
| `std(x)` | стандартное отклонение |
| `z_score(x)` | отклонение значения от среднего в единицах стандартного отклонения |

`safe_div` лучше, чем `max(denominator, 1)`, потому что подмена нулевого знаменателя единицей может создать ложную точность. Если данных для отношения нет, это должно быть видно в UI.

## 1. Баланс потоков

Анализ входящих и исходящих значений.

Типовые игровые смыслы:

- ресурс начисляется;
- ресурс тратится;
- значение производится;
- значение потребляется;
- запас растёт или уменьшается.

### Примеры вопросов

| Общий вопрос | Игровая иллюстрация |
|---|---|
| Ресурс копится или исчезает? | Как если бы разработчик `Stardew Valley` проверял, не копится ли золото быстрее, чем игрок успевает тратить его на семена, инструменты и здания. |
| Расход соответствует доходу? | Как если бы разработчик `Hades` проверял, не слишком ли быстро игрок тратит Darkness, Keys или Gems относительно темпа их получения между забегами. |
| Есть ли признаки инфляции? | Как если бы разработчик `Vampire Survivors` проверял, не становится ли золото к середине прогрессии настолько избыточным, что цены улучшений перестают иметь значение. |
| Как меняется чистый поток по окнам наблюдения? | Как если бы разработчик `Factorio` сравнивал, на каких этапах фабрика производит ресурсы быстрее, чем система исследований и строительства их потребляет. |

### Переменные

| Переменная | Описание | Обязательная |
|---|---|---|
| `flow_in` | входящее значение | да |
| `flow_out` | исходящее значение | да |
| `stock_start` | запас в начале окна | нет |
| `stock_end` | запас в конце окна | нет |
| `duration` | длительность окна | нет |
| `context` | источник, sink, режим, билд, категория | нет |

### Метрики

| Метрика | Формула | Интерпретация |
|---|---|---|
| Чистый поток | `Σflow_in - Σflow_out` | положительное значение указывает на накопление, отрицательное — на дефицит |
| Доля расхода к доходу | `safe_div(Σflow_out, Σflow_in)` | `> 1` — расход выше дохода, `< 1` — доход выше расхода |
| Изменение запаса | `stock_end - stock_start` или `Σflow_in - Σflow_out` | абсолютное изменение накопленного значения |
| Относительное изменение запаса | `safe_div(stock_end - stock_start, abs(stock_start))` | насколько сильно изменился запас относительно начального состояния |

### Ограничения

- Если нет `stock_start/stock_end`, изменение запаса можно оценивать по потокам, но это не заменяет реальный stock.
- Если входящий поток равен нулю, доля расхода к доходу должна быть `N/A`, а не `flow_out / 1`.
- Для разных ресурсов метрики считаются отдельно, если пользователь не задал явное правило объединения.

## 2. Динамика запаса

Анализ накопления, снижения, ускорения, замедления и плато значения во времени.

Типовые игровые смыслы:

- прогрессия силы;
- накопление ресурса;
- рост уровня;
- изменение сложности;
- изменение доступного набора действий.

### Примеры вопросов

| Общий вопрос | Игровая иллюстрация |
|---|---|
| Развитие ускоряется или замедляется? | Как если бы разработчик `Hollow Knight` смотрел, как быстро игроки получают новые способности, charms или доступ к зонам по ходу прохождения. |
| Запас выходит на плато? | Как если бы разработчик `Ori and the Blind Forest` проверял, не останавливается ли рост доступных улучшений после определённой части игры. |
| Есть ли резкий скачок прогрессии? | Как если бы разработчик `Dead Cells` проверял, не даёт ли один этап забега слишком резкий прирост силы по сравнению с соседними этапами. |
| Потери становятся значимыми относительно накопленного значения? | Как если бы разработчик survival-игры вроде `Don't Starve` проверял, не начинают ли потери здоровья, голода или sanity доминировать над восстановлением. |

### Переменные

| Переменная | Описание | Обязательная |
|---|---|---|
| `stock_value` | текущее значение запаса или прогресса | да |
| `stock_gain` | прирост | нет |
| `stock_loss` | потеря | нет |
| `timestamp` | время события | нет |
| `duration` | длительность окна | нет |
| `context` | стадия, билд, режим, сложность | нет |

### Метрики

| Метрика | Формула | Интерпретация |
|---|---|---|
| Изменение | `stock_t - stock_(t-1)` | абсолютный прирост или падение |
| Темп изменения | `safe_div(stock_t - stock_(t-1), Δt)` | скорость роста или падения |
| Относительное изменение | `safe_div(stock_t - stock_(t-1), abs(stock_(t-1)))` | изменение относительно предыдущего состояния |
| Относительная потеря | `safe_div(Σstock_loss, max(abs(stock_t), epsilon))` | насколько потери значимы относительно текущего значения |
| Плато | `abs(change_rate) < threshold` в течение `N` окон | развитие почти остановилось |
| Скачок | `abs(z_score(Δstock)) > threshold` | окно заметно выбивается из обычной динамики |

### Ограничения

- Плато и скачок требуют порогов, которые должны быть видны в настройках шаблона.
- Нельзя автоматически считать плато проблемой: в некоторых играх оно может быть намеренной стабилизацией.
- `stock_value` должен быть сопоставимым внутри одного ряда. Нельзя смешивать разные ресурсы без нормализации.

## 3. Эффективность конверсии

Анализ превращения одного значения в другое: ресурс → улучшение, время → результат, риск → награда, действие → прогресс.

Типовые игровые смыслы:

- окупаемость апгрейда;
- эффективность маршрута;
- полезность действия;
- стоимость единицы результата;
- сравнение альтернатив.

### Примеры вопросов

| Общий вопрос | Игровая иллюстрация |
|---|---|
| Окупается ли апгрейд? | Как если бы разработчик `Hades` проверял, даёт ли улучшение Mirror of Night заметный результат за свою цену. |
| Какой путь развития эффективнее? | Как если бы разработчик `Slay the Spire` сравнивал ценность удаления карты, покупки реликвии и апгрейда карты в разных контекстах забега. |
| Где цена не соответствует результату? | Как если бы разработчик `Into the Breach` проверял, не стоит ли одно улучшение меха слишком дорого относительно прироста боевой эффективности. |
| Не появился ли доминирующий вариант? | Как если бы разработчик `Balatro` проверял, не даёт ли один тип joker/синергии несоразмерный прирост результата относительно альтернатив. |

### Переменные

| Переменная | Описание | Обязательная |
|---|---|---|
| `cost` | затраты | да |
| `result` | полученный результат | да |
| `action_count` | число операций | нет |
| `context` | тип действия, категория, билд, этап | нет |
| `cost_value` | стоимость, приведённая к общей ценности | нет |
| `result_value` | результат, приведённый к общей ценности | нет |

### Метрики

| Метрика | Формула | Интерпретация |
|---|---|---|
| Результат на единицу затрат | `safe_div(Σresult, Σcost)` | сколько результата даёт единица затрат |
| Стоимость единицы результата | `safe_div(Σcost, Σresult)` | сколько стоит единица результата |
| Средний результат действия | `safe_div(Σresult, count(action_count))` | средняя отдача одной операции |
| Нормализованный ROI | `safe_div(Σresult_value - Σcost_value, Σcost_value)` | окупаемость, если cost и result приведены к сопоставимой шкале |
| Ранг альтернатив | `rank_by(result_per_cost, context)` | какие варианты выглядят сильнее или слабее внутри контекста |

### Ограничения

- `ROI = (result - cost) / cost` допустим только если `cost` и `result` измерены в сопоставимых единицах или приведены к общей шкале.
- Если `cost` — золото, а `result` — урон, система должна использовать “результат на единицу затрат”, а не притворяться, что это строгий финансовый ROI.
- Доминирующая стратегия требует сравнения альтернатив в похожем контексте. Без контекста это только сигнал для ручной проверки.

## 4. Давление стоимости

Анализ того, насколько стоимость ограничивает доступность действий.

Типовые игровые смыслы:

- цена апгрейда;
- цена покупки;
- требование ресурса;
- требование уровня;
- стоимость попытки;
- штраф за действие.

### Примеры вопросов

| Общий вопрос | Игровая иллюстрация |
|---|---|
| Слишком ли дорогая операция? | Как если бы разработчик `Terraria` проверял, не слишком ли рано крафт определённого предмета требует редкий ресурс. |
| Как часто действие недоступно из-за цены? | Как если бы разработчик `Hades` смотрел, как часто игрок хочет купить улучшение, но не имеет нужного ресурса после забега. |
| Какие требования чаще всего блокируют игрока/систему? | Как если бы разработчик `Factorio` проверял, какая технология или ресурс чаще всего тормозит переход к следующему производственному этапу. |

### Переменные

| Переменная | Описание | Обязательная |
|---|---|---|
| `cost` | стоимость действия | да |
| `available_resource` | доступное значение | да |
| `attempt` | попытка выполнить действие | нет |
| `blocked` | факт блокировки | нет |
| `required_value` | требуемое значение | нет |

### Метрики

| Метрика | Формула | Интерпретация |
|---|---|---|
| Давление стоимости | `safe_div(cost, available_resource)` | насколько цена велика относительно доступного значения |
| Запас доступности | `available_resource - cost` | насколько пользователь выше или ниже требования |
| Относительный запас доступности | `safe_div(available_resource - cost, cost)` | насколько требование далеко от доступного значения |
| Доля блокировок | `safe_div(count_if(blocked), count(attempt))` | как часто действие недоступно |

### Ограничения

- Высокое давление стоимости не всегда ошибка: оно может быть намеренным ограничителем.
- Для честного вывода нужны попытки или явные события блокировки. Одних цен недостаточно, чтобы понять реальную недоступность.
- Если действие никогда не пытались выполнить, нельзя отличить “слишком дорого” от “неинтересно”.

## 5. Доступность действий

Анализ доступных и недоступных операций.

Типовые игровые смыслы:

- попытка действия;
- успешное действие;
- заблокированное действие;
- причина отказа;
- требование к ресурсу, уровню, предмету, таймеру.

### Примеры вопросов

| Общий вопрос | Игровая иллюстрация |
|---|---|
| Какие действия чаще всего не удаётся выполнить? | Как если бы разработчик `Dead Cells` проверял, какие двери, мутации, предметы или улучшения чаще всего остаются недоступными в забегах. |
| Как меняется доступность по прогрессии или билдам? | Как если бы разработчик `Hollow Knight` сравнивал, как часто игроки упираются в закрытые зоны до и после изменения порядка получения способностей. |
| Какой лимит чаще всего срабатывает? | Как если бы разработчик `RimWorld` проверял, какой ресурс, навык или условие чаще всего блокирует производство, строительство или лечение. |

### Переменные

| Переменная | Описание | Обязательная |
|---|---|---|
| `attempt` | попытка операции | да |
| `success` | успешное выполнение | да |
| `blocked` | заблокированная операция | нет |
| `block_reason` | причина блокировки | нет |
| `requirement_value` | требование | нет |
| `available_value` | доступное значение | нет |

### Метрики

| Метрика | Формула | Интерпретация |
|---|---|---|
| Доля успешных операций | `safe_div(count_if(success), count(attempt))` | какая часть попыток завершается успешно |
| Доля блокировок | `safe_div(count_if(blocked), count(attempt))` | какая часть попыток блокируется |
| Топ причин блокировки | `group_count(block_reason)` | какие причины чаще всего закрывают действие |
| Средний разрыв требования | `mean(requirement_value - available_value)` для blocked-событий | насколько пользователь в среднем не дотягивает до требования |

### Ограничения

- Для недоступности нужны именно попытки или явные блокировки. Если система не логирует отказ, BalanceCraft может только предполагать проблему.
- `success` и `blocked` должны быть взаимоисключающими в рамках одной попытки или явно разделены по event_type.
- Топ причин блокировки полезен только при стабильной таксономии `block_reason`.

## 6. Интенсивность операций

Анализ частоты событий за окно наблюдения.

Типовые игровые смыслы:

- действий в минуту;
- боёв за забег;
- смертей за участок;
- покупок за окно;
- крафтов за период;
- полученного результата за время.

### Примеры вопросов

| Общий вопрос | Игровая иллюстрация |
|---|---|
| Игровая система становится более или менее активной? | Как если бы разработчик `Vampire Survivors` отслеживал число убийств, поднятых gems или level-up событий в минуту. |
| Есть ли участки гринда? | Как если бы разработчик `Hollow Knight` смотрел, сколько повторяющихся боёв требуется для покупки нужного предмета. |
| Получает ли пользователь достаточно результата за время? | Как если бы разработчик `Celeste` проверял, не превращается ли участок в слишком длинную серию смертей без продвижения. |
| Не проседает ли темп системы? | Как если бы разработчик `Factorio` смотрел, не падает ли частота completed production cycles после расширения фабрики. |

### Переменные

| Переменная | Описание | Обязательная |
|---|---|---|
| `action` | действие или событие активности | да |
| `duration` | длительность окна | да |
| `reward` | полученный результат | нет |
| `timestamp` | время события | нет |
| `context` | зона, билд, режим, этап | нет |

### Метрики

| Метрика | Формула | Интерпретация |
|---|---|---|
| Интенсивность | `safe_div(count(action), duration)` | событий за единицу времени |
| Эффективность времени | `safe_div(Σreward, duration)` | результат за единицу времени |
| Действий на результат | `safe_div(count(action), Σreward)` | сколько действий нужно на единицу результата |
| Средний интервал действий | `mean(delta_time_between_actions)` | насколько часто происходят события |

### Ограничения

- Высокая интенсивность не всегда означает хорошую вовлечённость: это может быть гринд или шумное логирование.
- Для сравнения разных игр и режимов нужна одинаковая единица времени или observation.
- Если события пишутся слишком часто, лучше агрегировать их на стороне игры или импорта.

## 7. Использование контента

Анализ того, какие действия, объекты, апгрейды или опции реально используются и какой результат дают.

Типовые игровые смыслы:

- оружие;
- карты;
- способности;
- апгрейды;
- предметы;
- маршруты;
- здания;
- юниты;
- рецепты;
- опции диалога.

### Примеры вопросов

| Общий вопрос | Игровая иллюстрация |
|---|---|
| Есть ли действия или объекты, которые почти не используются? | Как если бы разработчик `Hades` проверял, какие boons, weapons или keepsakes почти не выбираются в забегах. |
| Какие опции дают плохой результат относительно стоимости? | Как если бы разработчик `Slay the Spire` смотрел, какие карты часто берут, но они редко приводят к успешному прохождению акта. |
| Игроки концентрируются на одной стратегии или используют альтернативы? | Как если бы разработчик `Dead Cells` сравнивал, не доминирует ли один тип оружия или мутации в большинстве успешных забегов. |
| Есть ли мёртвый контент? | Как если бы разработчик `Terraria` проверял, какие рецепты, предметы или аксессуары почти никогда не создаются и не используются. |

### Переменные

| Переменная | Описание | Обязательная |
|---|---|---|
| `content_id` | идентификатор действия, объекта, апгрейда или опции | да |
| `usage` | факт использования | да |
| `cost` | стоимость использования | нет |
| `result` | полученный результат | нет |
| `context` | режим, билд, этап, категория | нет |
| `success_marker` | маркер успешного исхода | нет |

### Метрики

| Метрика | Формула | Интерпретация |
|---|---|---|
| Частота использования | `count(usage) grouped by content_id` | какие элементы используются чаще или реже |
| Доля использования | `safe_div(count(content_id), count(all_usage))` | вес элемента среди альтернатив |
| Доля топ-элемента | `max(usage_share)` | насколько сильно доминирует один вариант |
| Эффективность элемента | `safe_div(Σresult, Σcost)` | результат элемента относительно цены, если есть cost/result |
| Успешность использования | `safe_div(count_if(success_marker), count(usage))` | как часто использование связано с успешным исходом |

### Ограничения

- Низкое использование не всегда означает плохой баланс: контент может быть редким, поздним или нишевым.
- Доминирование одного варианта требует сравнения внутри корректного контекста: билд, стадия, сложность, тип игрока/забега.
- Успешность использования не доказывает причинность: сильные пользователи могут выбирать сложный контент чаще.

## 8. Ритм наград

Анализ частоты, регулярности и неравномерности выдачи наград или других значимых результатов.

Типовые игровые смыслы:

- награды за комнату;
- выпадение предметов;
- level-up;
- получение валюты;
- открытие способности;
- успешное завершение шага;
- редкий drop.

### Примеры вопросов

| Общий вопрос | Игровая иллюстрация |
|---|---|
| Награды приходят слишком редко или слишком часто? | Как если бы разработчик `Hades` проверял, не слишком ли длинные участки забега проходят без meaningful reward. |
| Есть ли длинные участки без результата? | Как если бы разработчик `Ori and the Will of the Wisps` смотрел, не слишком ли долго игрок идёт между заметными улучшениями или находками. |
| Не создаёт ли система резкие пики наград? | Как если бы разработчик `Balatro` проверял, не приводит ли один момент магазина к чрезмерному скачку силы по сравнению с остальной партией. |
| Насколько стабилен ритм вознаграждения? | Как если бы разработчик `Stardew Valley` сравнивал регулярность дохода между рыбалкой, фермерством и шахтой. |

### Переменные

| Переменная | Описание | Обязательная |
|---|---|---|
| `reward` | полученная награда или результат | да |
| `timestamp` | время события | да |
| `duration` | длительность окна | нет |
| `context` | источник, тип награды, режим | нет |
| `reward_value` | числовая ценность награды | нет |

### Метрики

| Метрика | Формула | Интерпретация |
|---|---|---|
| Частота наград | `safe_div(count(reward), duration)` | как часто выдаётся результат |
| Средний интервал | `mean(delta_time_between_rewards)` | сколько времени проходит между наградами |
| Медианный интервал | `median(delta_time_between_rewards)` | типичный интервал без влияния редких выбросов |
| Неровность наград | `std(delta_time_between_rewards)` | насколько ритм нестабилен |
| Коэффициент вариации интервалов | `safe_div(std(intervals), mean(intervals))` | относительная неровность ритма |
| Максимальный разрыв | `max(delta_time_between_rewards)` | самый длинный участок без награды |

### Ограничения

- “Хороший” ритм зависит от жанра. Для roguelike, metroidvania, deckbuilder и survival разные нормы.
- Если награды имеют разную ценность, частота без `reward_value` может быть недостаточной.
- Очень частые мелкие награды и редкие крупные награды нужно анализировать отдельно.

## 9. Нестабильность динамики

Анализ резких изменений, выбросов и чувствительности временных рядов.

Типовые игровые смыслы:

- резкий скачок экономики;
- внезапный перелом прогрессии;
- нестабильная сложность;
- чувствительность к малому изменению параметра;
- подозрительный участок данных.

### Примеры вопросов

| Общий вопрос | Игровая иллюстрация |
|---|---|
| Есть ли точки резкого изменения баланса? | Как если бы разработчик `Balatro` смотрел, где конкретная комбинация резко ломает кривую счёта или денег. |
| Близкие состояния системы расходятся или сходятся? | Как если бы разработчик `RimWorld` сравнивал колонии с похожим стартом и проверял, не расходятся ли они из-за малого различия в ресурсах или событиях. |
| Где требуется ручная проверка событий? | Как если бы разработчик `Hades` искал забеги, где прирост силы или валюты резко отличается от соседних забегов того же этапа. |
| Не слишком ли шумная метрика? | Как если бы разработчик `Dead Cells` проверял, не делает ли один источник урона или наград весь ряд слишком скачущим для нормальной настройки. |

### Переменные

| Переменная | Описание | Обязательная |
|---|---|---|
| `metric_series` | один или несколько временных рядов метрик | да |
| `timestamp` или `x_index` | порядок точек | да |
| `context` | билд, режим, сложность, группа | нет |

### Метрики

| Метрика | Формула / основа | Интерпретация |
|---|---|---|
| Волатильность изменений | `std(Δmetric_series)` | насколько ряд скачет между окнами |
| Относительная волатильность | `std(percent_change(metric_series))` | насколько сильны скачки относительно масштаба ряда |
| Точка резкого изменения | `abs(z_score(Δmetric_series)) > threshold` | окно заметно отличается от обычной динамики |
| Коэффициент вариации | `safe_div(std(metric_series), mean(metric_series))` | относительный шум ряда |
| Оценка устойчивости | сравнение нескольких рядов или траекторий | предварительная оценка чувствительности системы |

### Ограничения

- Нестабильность динамики — P1/P2-область, а не обязательный P0.
- Волатильность и выбросы показывают симптом, но не объясняют причину без дополнительного контекста.
- Оценка устойчивости не должна выглядеть как строгая математическая гарантия, если нет заданной модели системы.

## MVP-набор шаблонов

Для BalanceCraft 1.5 минимально достаточно P0-набора:

1. Баланс потоков.
2. Динамика запаса.
3. Эффективность конверсии.
4. Интенсивность операций.

P1-набор, если хватает времени после базового vertical slice:

1. Давление стоимости.
2. Доступность действий.
3. Использование контента.
4. Ритм наград.

P2-набор:

1. Расширенная нестабильность динамики.
2. Доминирующие стратегии с полноценным сравнением альтернатив.

Важно: наличие проблемы в таксономии не означает обязательную поддержку в P0. UI должен показывать, какие проблемы текущий набор данных и текущая версия продукта действительно могут проверить.
